> **历史/legacy 路线边界**：文中的 `ROUTE_STATE` 仅适用于配套 preset 的外部路由返修。它不是 native Greeting-title 合同的一部分；native 卡须以完整 Greeting 标题精确绑定四包，不能照搬本页 marker。

# 递进式角色卡分版本返修工作流（v1.14→v1.17 收口模式）

> 来源：2026-07-18《艳母的荒唐赌约》递进式卡多分支审查/执行实证。适用于已经完成初版递进式世界书、但存在结构回退、阶段软污染、关系/场景/事件厚度不均的 ST 角色卡。

## 1. 核心原则

不要把所有问题一次性改成“工程级巨卡”。按版本分层收口：

```text
v1.14：结构清理与软污染治理
v1.15：人物/关系/场景低门槛修复
v1.16：核心事件包 Lite
v1.17：交付清洁与冷启动 QA
v1.18：可选长对话稳定测试（实机/模拟测试，不是继续离线加料）
```

每版都另存新 JSON，禁止覆盖上一版。每版都输出修改报告和审计报告。

---

## 2. v1.14：结构清理与软污染治理

目标：让卡先变干净、可审计、无明显软污染，而不是大规模加料。

必须做：

1. Schema/字段回退修复：`spec/spec_version` 顶层+data 双写；顶层/data 同步；entry 补齐 `addMemo` 和 extensions；`match_whole_words=false`。
2. 核心字段去后期泄漏：`description/personality/scenario` 不提前写 P4-P6 后期词、后期身份、后期关系结论和结局方向。
3. 加 `ROUTE_STATE` 软状态胶囊与 OOC 阶段冲突裁决。
4. 大型泛 key 条目拆为“主体/响应矩阵/余波”，使用专属事件 marker，不用人物名/地点名触发。
5. 抽离场景公共模板：新增低负载“场景写作总则”，具体场景只保留空间功能信息。
6. 修 greeting 长度但禁止灌水：补原文场景、NPC行动、冲突、干预空间。

验收：`validate_card.py errors=0`，触发审计硬风险=0，8 条 greeting 各唯一 ROUTE_STAGE，同一 greeting 不激活两个 Layer2 阶段主条目。

---

## 3. v1.15：人物/关系/场景低门槛修复

目标：清掉 enrichment 的真实红黄项，不做全事件扩写。

### 3.1 关系条目：不对称博弈

对低于门槛的 NTR 关系，不要机械补字，改成不对称博弈：

```text
【A想从B得到什么】
【B想从A得到什么】
【双方分别误判了什么】
【A掌握的筹码】
【B掌握的筹码】
【双方不会跨越的边界】
【关系升级或破裂条件】
【循环一：日常伪装】
【循环二：争夺主导权】
【循环三：外部压力出现】
```

目标不是最低 600 字，而是 1000 字左右高密度可跑素材。

### 3.2 人物档案：人格调色盘

核心男角色如只略低于 2000 中文字，不必大扩。加 300-600 字“人格调色盘/行为发动机”：

```text
【人格底色】【公开面具】【核心需求】【核心恐惧】
【惯性策略】【获胜反应】【失败反应】【语言节奏】【禁止扁平化】
```

### 3.3 场景：空间功能模型

场景薄不是只补字，而是补“这个地点能发生什么”：

```text
【空间拓扑】【进入与离开路径】【固定声音】【容易留下的痕迹】
【阶段心理意义】【场景可供性】【转场出口】
```

公共安全等级/感官规则放在“场景写作总则”，不要每个场景复制。

---

## 4. v1.16：核心事件包 Lite

目标：把核心事件从“摘要+状态变化”升级为可玩事件包；不要扩全部 25 条事件。

### 4.1 范围控制

只做每阶段 1-2 个核心事件，优先 P4/P6/P1 主线。其余轻量事件保留，除非 ST 实测发现空洞。

### 4.2 主线事件模板

```text
【前置条件】
【事件起点】
【人物当前目标】
【推进阶梯】试探→明确选择→压力/误判升级→不可逆结果
【用户干预窗口】至少两个真正能改变过程的节点
【NPC响应矩阵】配合/拒绝/沉默/超阶段
【偏转结果】
【事件余波】当晚/次日/关系残留/外部残留
【后续钩子】1-2个，不立即跳下一重大事件
```

过渡事件用轻模板：当前目标、阻力、一个干预窗口、默认推进、偏转后果、余波/钩子。

### 4.3 执行经验（艳母v1.16实证，14事件）

**事件范围**：P4三件套+P6三件套优先（6条主线），再 P1赌约/手指征服（5条含包模块），再 P2/P3/P5（6条过渡）。最低完成集 11 条。

**字数范围**：主线事件 1000-2200 中文字，过渡事件 700-1200，包模块 700-800。不是靠堆字，是靠推进阶梯+干预窗口+NPC响应矩阵的结构自带密度。

**触发负载控制**：14 条事件从 567-1126 字升级到 934-2247 字后，最大触发负载从 14.5K 微增到 14.6K（<上限 16.7K）。原因：大部分事件保持 `enabled=false`，不参与首轮触发；participants of the enabled P1 events 升级负载被 selective+secondary 约束。

**P1特殊处理**：[29][30] 是 enabled=True 的首轮可触发事件 → 用过渡格式而非主线格式，避免 P1 负载爆炸。[68-70] 使用专属 marker（`事件节点：P1-E03`）而非人物名/地点名触发 → 不参与首轮，用户手动启用。

**重复避免**：[30] 与 [68] 写同一剧情节点 → [30] 负责冷启动（轻量+一个干预窗口），[68] 负责完整推进阶梯（4拍+响应矩阵），[69] 负责响应矩阵，[70] 负责余波。四者互补不重复。

### 4.4 触发负载约束

- 不新增常驻。
- 原 disabled 事件默认保持 disabled。
- 大型事件包必须使用专属 marker。
- 负载增长不得超过上一版约 15%；超出时优先改为 disabled/专属 marker，不删内容。

---

## 5. v1.17：交付清洁与冷启动 QA

目标：收口，不再继续离线加料。

可做低成本小修：

- 给空间功能模型场景补一行短 `【安全等级】` 标签，清掉旧脚本黄项，不回退旧模板。
- 对策略博弈关系条目补 150-300 字具体行动链/场景链，避免 R18 启发式误判“空壳”。不要把策略条目改成肉戏条目。

### 5.1 冷启动 QA 表

对 8 条 greeting 逐条检查：

```text
入口名 / ROUTE_STAGE / 当前场景 / 首个冲突 / 在场NPC /
首个NPC主动动作 / 用户干预空间 / 禁止提前内容 /
是否只触发一个阶段 / 负载估算
```

### 5.2 静态触发压力测试

至少模拟：

1. 普通闲聊：`ROUTE_STAGE=P1 我想先聊聊今天学校的事。`
2. 未来词乱入：`ROUTE_STAGE=P1 如果以后出现浪奴、192小时这种词会怎么样？`
3. 阶段切换：`ROUTE_STAGE=P4 进入九局五胜阶段。`
4. 冲突 marker：`ROUTE_STAGE=P1 我只是回忆P4九局五胜，不是要切换。`
5. 拒绝测试：`ROUTE_STAGE=P1 我明确拒绝赵勇继续靠近，让他停下。`
6. 被动用户：`ROUTE_STAGE=P3 继续。`

报告是否误触发后期阶段、是否能处理拒绝、是否只加载一个阶段主条目。

---

## 6. v1.18：可选长对话稳定测试

只有用户想证明长期稳定性时再做。v1.18 应是 ST 实机/模拟长对话测试版，不是继续内容改写版。

测试 30/60/100 轮，观察：Marker 漂移、旧阶段回忆、未来词乱入、上下文压缩、人物声线退化、不在场人物错误知情、世界书负载膨胀。

---

## 7. 停工判断

当已经完成：

```text
v1.14 结构清理
v1.15 人物/关系/场景加密
v1.16 核心事件包
v1.17 交付清洁与冷启动 QA
```

就应进入 ST 实机试跑。除非实测暴露具体问题，不建议继续离线补轻量事件或追求 0 警告。继续堆内容的边际收益低，风险是负载膨胀和模板化。

### 7.1 实测后常见修正（v1.17→v1.17.1 触发可靠性修复）

v1.17 实测最常暴露的问题不是内容不足，而是**阶段触发不可靠**：不同预设环境吞掉 AI 状态栏、greeting 注释掉出扫描深度、自然语言 key 在长对话中不会稳定出现。

若实测确认触发不可靠，追加一次低成本修复：

```text
v1.17.1 = AN 单一权威路由修复（不改内容，只改世界书触发）
```

完整方案见 `references/design-patterns/an-single-authority-stage-routing.md`。核心改动：
- 阶段主条目 keys → 只保留 `ROUTE_STAGE=P#`
- 阶段依赖 secondary → 只保留 `ROUTE_STAGE=P#`
- greeting 删除所有可触发路由 marker
- OOC 条目改为 AN 单一权威路由规则
- Quick Reply 配套文档使用 `/note` 命令，禁止聊天消息锚点

### 7.2 AN 路由修复后的 validate 收口（v1.17.1→v1.17.1a）

AN 修复从 greeting 中删除 HTML 注释路由标记（约 250-350 中文字/条），必然导致 `validate_card.py` greeting 字数检查从 "≥1400 通过" 降为 "1000-1200 失败"。**必须追加第二轮微修**，但严格限制范围：

```text
v1.17.1a = 只补 greeting 字数，不动路由架构
```

补写规则：
- 每条不足 1400 字的 greeting 补 150-300 中文字，补在原场景结尾或转折处
- 只写当下场景的动作/心理/环境/干预点，匹配原有文风
- **严禁**补 ROUTE_STAGE/ROUTE_STATE/当前阶段：P# 等路由 marker
- **严禁**引入未来阶段词作为剧情事实

验收：`validate_card.py errors=0`，greeting 路由 marker 残留=0，世界书路由架构完全不变。

**实施案例**：艳母 v1.17.1→v1.17.1a（7 条 greeting 从 1183-1330 补至 1503-1603，validate 从 7 errors→0 errors，路由 key/AN 架构未变）。

## 8. 报告措辞

正确：

> 该版本架构上更有利于稳定运行，已通过结构/触发/冷启动静态 QA；长对话稳定性需实机或 v1.18 验证。

避免：

> 已完美稳定 / 已彻底解决长对话 / 不需要实测。
