# 角色卡横向对比审查工作流

> 适用：用户要求“对比两张卡/哪张更好/别人做的 vs 我们做的”时。目标不是立刻修卡，而是给出客观判断：哪张更适合跑卡、哪张更适合拆素材、各自风险在哪里。

## 1. 基本原则

1. **先审查，不默认修改**：用户问“哪张好一点”时，先比较与评价，不要直接动手返修，除非用户随后说“执行/修”。
2. **区分三种“好”**：
   - 素材厚度/局部文笔：条目长、路线多、描写浓。
   - 跑卡稳定性：触发负载、阶段隔离、ST字段、常驻数量、selective/secondary是否正确。
   - 交付合规性：validate/audit/enrichment是否通过，是否有构建残留、开场白不足、addMemo/扩展字段缺失。
3. **不要用文件大小直接判胜负**：大卡可能只是变量系统/常驻规则/全局污染堆出来；小卡可能架构更稳但素材偏薄。
4. **给“双层结论”**：例如“作为主卡我们这张更好；作为素材库参考卡更有价值”。避免简单二选一。

## 2. 必跑检查

对两张卡都做同一套量化审查：

- JSON结构与ST字段：`spec/data.spec/spec_version`、top/data同步、world绑定、entry extensions完整性。
- 世界书统计：文件大小、条目数、enabled/disabled、constant/selective、secondary_keys、position、match_whole_words。
- 开场白：数量、长度、是否有阶段注释、相似度/重复段、是否基于原文场景。
- 触发负载：运行 `audit_worldbook_triggers.py`，比较每个greeting首轮常驻+触发条目及风险条目。
- 内容厚度：运行 `enrichment_self_check.py --r18 --prototype <A/E/G...>`，注意红项/黄项；另外单独统计事件种子的【事件核心叙事】长度。
- 抽读样本：至少抽读 top fields、1个核心角色、1个阶段条目、1个关系条目、1-2个事件种子、1个场景/反击/结局条目。

## 3. 判断框架

### 3.1 参考卡常见优点

- 大量路线/阶段/NSFW调色盘，局部素材很厚。
- 变量系统、MVU、getvar/setvar、控制器等工程化程度高。
- 开场白可能更长、更有叙事进入感。

### 3.2 参考卡常见风险

- 依赖特定预设/脚本环境，不一定单卡导入即稳定。
- 常驻条目过多导致首轮触发负载巨大。
- primary-only、无secondary阶段绑定，可能发生阶段污染。
- description/personality/scenario空或无效。
- 总量很大但人物档案、关系条目、语料库可能反而薄。

### 3.3 我们卡常见优点

- 阶段状态机清楚，P0-P6或多视角身份隔离明确。
- `secondary_keys` 绑定阶段marker，降低旧素材/后期素材污染。
- 中文卡 `match_whole_words=false`，触发更可靠。
- top fields 写实际人物和剧情，而不是架构注释。
- 多开场白作为阶段入口，适合递进式玩法。

### 3.4 我们卡常见风险

- 架构正确不等于内容足够：事件种子、场景、关系条目可能偏薄。
- 后期补强条目可能形成大条目/泛key/extension selective不一致。
- validate通过或接近通过不代表可交付；enrichment红项和事件核心叙事不足仍需返修。

## 4. 输出格式建议

用短结论开头：

> 结论：如果按“实际跑卡稳定性/可控性”，A更好；如果按“素材总量和局部文笔浓度”，B更强。

随后给：

1. 核心数据表。
2. A卡优点/问题。
3. B卡优点/问题。
4. 最终判断：主卡选择、素材借鉴选择、是否达到交付线。
5. 如需返修，列3-5个最高优先级，不要在用户只问评价时直接修改。

## 5. 实战判语模板

- “这不是碾压。A赢在素材厚度，B赢在架构和跑卡稳定性。”
- “第一张适合拆素材，不适合直接当最终卡。”
- “我们这张方向更正确，但事件种子/场景/关系还要补厚。”
- “文件大小不是胜负，触发负载和阶段污染更决定实际跑卡体验。”
