# 原型判定前置体检：已拆分长篇小说目录

> 适用：用户给的是一个小说目录（已按章节拆分，常伴随“小说分析记录.md”），并要求先做前置分析再判定卡型。

## 目的

在跑 §1.0 原型判定决策树之前，先获得足够事实基础，避免“看到NTR/催眠关键词就套A型”或“看到多个男性角色就机械做G型”。

这一步不是完整制卡分析；它是**原型判定前的目录体检与关系预检**。原型确认后仍需按计划书阶段继续做模板匹配、章节精读、条目规划。

## 最小必做输出

1. **目录结构**
   - 文件总数；章节txt数量；分析md/json等辅助文件数量
   - 章节号范围、跳号/缺号、是否疑似合集大txt
   - 是否需要合集拆分/章节拆分；若已是单章文件，明确“不需要拆分”
   - **已有卡/世界书评估**：如果目录内已有 .json 角色卡，检查 spec 版本（v2 vs v3）、条目数量、文件大小，判断可复用 vs 需完全重做
2. **规模统计**
   - 总字符/中文字数、平均每章长度
   - 重复文件检测（至少MD5完全重复）
3. **机制/题材关键词分布**
   - 搜索核心机制词（如系统、催眠、脑机接口、贡献点、助理、NTR、男友等）
   - 输出次数、章节覆盖、初次/末次出现
4. **人物频次与关系锚点预检**
   - 主要人物提及次数、章节覆盖、首次/末次
   - 高频别名归并（如同一人的代号/昵称）
   - 关系锚点：血缘、恋人/前任、上下级、组织归属、被控制/征服关系
5. **角色名混淆预警**
   - 同音/形近/别名混淆（如“卫璎” vs “媖子”）
   - 头衔混淆（如“老李”不是“李志峰”；“李主任/李总”随时间线变化）
   - 亲属称谓必须写绝对参照（如“秦燕霞是杨玉兰的母亲”，禁止裸写“妈妈”）
6. **角色名本地化检查**
   - 逐个检查角色名是否有真实民族/国籍/宗教色彩
   - 架空历史（大秦/大周/大梁等）+传统中国风格名字 → 无风险，直接通过
   - 真实国名/民族名+身体描写组合 → 必须在计划书列出改名方案
   - 案例：道家仙子美母全部角色名为架空历史中国传统名，零风险

7. **系统权重评估**
   - 如果小说有"系统"设定（修真功法/游戏系统/催眠机制/脑机接口等），判断它是：
     - **A级核心机制**：直接驱动剧情、影响NTR推进、需要独立条目+阶段追踪
     - **B级催化剂**：辅助推进但非主线驱动力，融入世界观条目即可
     - **C级背景设定**：纯世界观装饰，仅在世界观条目提及
   - 判断标准：该机制是否是NTR/剧情推进的必要条件？去掉它剧情是否还能成立？
   - 案例：闭宫之术→A级（去掉后裴昭霁不会性欲失控→寰冲无法利用弱点→NTR不成立）

   ### 赌约/协议/契约类机制的特殊处理（pitfall）

   当小说包含**赌约、协议、契约、对赌**等约束性机制时，必须同时扫描：
   - **赌约**（wager/bet）：双方打赌，结果驱动剧情转折
   - **协议/契约**（agreement/contract）：正式的约束性文件，含条款、违约惩罚、执行条件

   ⚠️ **两者是不同的控制层级，不能只写赌约不写协议。** 赌约是"为什么开始"，协议是"怎么控制"。典型控制链：赌约→引发事件→协议锁定结果→违约惩罚→升级协议。

   系统权重评估时，赌约和协议/契约**各自独立评估**，不能合并为一条。如果两者都是A级，计划书中必须分别做结构化编码（条款正文、违约条件、惩罚机制、升级路径）。

   案例：艳母的荒唐赌约→三次赌约（第一/第二/骆鹏赌约）+两次协议（九局五胜对赌协议/192小时惩罚协议），均为A级核心机制。用户明确要求"三次赌约和两次协议"都要结构化增强。

8. **§1.0 决策树判定摘要**
   - 用上面的证据判断是否自然适配G型、传统NTR三角、C型征服者、E型禁忌后宫、F型观察者等
   - 如果多个可行，用 clarify 让用户确认原型/切入范围

## 推荐统计脚本思路

- 用 Python 遍历目录，不用手工目测。
- 章节号解析要同时支持：`第123章`、`第一二三章`、`第一二三章 标题`、`第二四七章 ...`。
- 编码读取按 `utf-8-sig → utf-8 → gb18030/cp936` 尝试。
- 对每章统计：字符数、中文字数、行数、MD5。
- 对人物别名建立字典，例如：
  - `李志峰`: `李志峰/志峰/李总/李主任`
  - `娄琛雨`: `娄琛雨/琛雨/雨燕`
  - `江天炜`: `江天炜/张鹏远/猎鹰`
- 关系预检不要只靠标题；需扫描正文中的短句样本，抓“母亲/男友/前女友/助理/特工/姐妹会/上司/下属”等关系词。

## 判定原则

- **机制词高频且贯穿全文**（如员工系统/脑机接口/贡献点）→ 优先考虑系统/玩法/征服者结构，不要只按表层NTR词判定。
- **传统NTR三角只是局部元素**（某角色有男友/前男友）但主线是主角掌权 → 通常不做A型苦主NTR。
- **多个男性角色存在**不等于自然G型；G型要求多个可玩身份都有完整可玩线，且多视角能提高体验而非稀释主线。
- 用户给出倾向目标时，也要用证据验证适配性；可以接受用户目标，但必须说明改造代价和边界。

## 交付格式建议

先用 clarify 给用户一个简洁但证据充分的选择摘要：

- 目录/章节/字数统计
- 拆分判断
- 核心机制计数
- 高频人物与关系锚点
- 混淆预警
- 角色名本地化风险（如有）
- 系统权重评估（A/B/C级）
- 决策树判定与1-4个原型选项

用户确认后，才写完整计划书；计划书确认后，才构建JSON。
