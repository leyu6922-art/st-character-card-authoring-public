# 变体卡生产流程（2026-07-11异世界卡验证）

## 适用场景
从已有NTR卡改造为NTL/守护/反杀等变体卡。

## 完整流程

### Phase 1：需求分析
1. 读取原版卡JSON，理解全部条目结构
2. 读取原版规划书（如有）
3. 用户确认变体方向（NTL夺回/守护/反杀等）
4. 写规划书→用户审阅→确认后再动JSON

### Phase 2：JSON构建
1. 复制原卡为独立文件
2. 用3个并行子代理写改/新条目（Batch1:核心系统 / Batch2:角色+场景 / Batch3:新增系统）
3. 合并脚本组装最终JSON
4. **合并后必做**：补全extensions/addMemo/position映射、清空constant条目keys、禁用被替代条目

### Phase 3：双轨审查
1. `validate_card.py` 35项结构检查（见`scripts/validate_card.py`）
2. Agent人工审查（6维度：first_mes质量/堕落轨迹一致性/NPC逻辑/旁白格式/系统完整性/设定一致性）
3. 修复→重跑validate_card验证

### Phase 4：交付
1. Discord简介.md（≤2000字符，用`assert len(content)<=2000`验证）
2. 角色卡JSON复制到桌面目录

## 变体卡必改清单

## 基于现有卡的增量构建（用户要求"不用从头开始"）

当已有2+个版本（如NTR版+守护版），用户要求在此基础上做新变体时：

1. **双版本复用分析**：读取所有现有版本的全部条目，逐条分类为：
   - **直接复用**（角色档案、描写库等不变内容）→ 复制，不改
   - **微调复用**（视角变化但内容基本不变）→ 复制后patch关键段落
   - **重写**（{{user}}身份变化导致的全局规则/状态栏/开场白等）→ 标记为"100%重写"
   - **新增**（新变体独有的系统，如赌场经营/唤醒系统等）→ 标记为"新增"
2. **规划书必含复用分析表**：列出每个条目的ID、名称、改造方式（复用/微调/重写/新增），让用户一眼看出工作量
3. **先做一张确认后再做其余**：多张变体卡时，先做一张完整的确认效果，再做其余

## 多视角NTL设计（同一小说→多张独立NTL卡）

当一部小说有多个NTR男性角色，每个都可作为独立的NTL {{user}}时：

**设计模式**：每个NTR男性 → 一张独立NTL卡
- {{user}} = 该NTR男性（如黑巨汉/兽人将军/爱德）
- 目标 = 原作中被NTR的女性角色
- 原苦主 = NPC（保留废物设定，反抗但永远失败）
- 其他NTR男性 = 竞争者/盟友（NPC）

**每张卡的差异化维度**：
| 维度 | 设计要点 |
|------|---------|
| 寝取手段 | 每个{{user}}有独特的征服方式（金钱/暴力/法杖/心机） |
| 难度曲线 | 每个女主对不同手段的抵抗力不同 |
| 竞争关系 | 其他NTR男性与{{user}}的合作/对抗动态 |
| 苦主反应 | 苦主对不同征服者的反抗方式和失败模式 |
| 开场白 | 每张卡从{{user}}视角展示其独特手段 |

**共用素材**：角色档案（四女+NTR男性）可跨卡复用，只需微调"对当前{{user}}的反应"。

**执行策略**：先做一张卡（用户指定优先级），确认效果后再做其余。并行做容易互相干扰且用户无法同时审查。


### 多视角世界观情感滤镜（多卡套装专用）

### 问题

同一世界观从不同{{user}}视角描述时，**事实不变但感情色彩/价值判断必须整体转换**。NTL转换指南（`ntl-perspective-conversion.md`）只说了"改条目视角+数据"，没说世界观描述要整体重新着色。

### 案例

| 制度事实 | 苦主版着色 | NTL版着色 |
|---------|-----------|----------|
| 天仙配APP配对 | "奴役国女的工具" | "赋予黑人的特权" |
| 抑Y药物 | "剥夺生育权的压迫" | "人口优化的保障" |
| 黑人街 | "法外之地·恐惧来源" | "自由之地·权力来源" |

### 适用场景

| 适用 | 不适用 |
|------|-------|
| ✅ 多视角卡套装（苦主版+NTL版+守护版） | ❌ 单张卡独立制作 |
| ✅ 同一世界观下做3+张不同视角的卡 | ❌ 同一张卡内不同视角 |
| ✅ 世界观制度/元素在不同视角下有截然不同的情感评价 | ❌ 事实本身不带价值判断 |

### 三步法

**Step 1：列出共享世界观元素清单**

涉及情感评价的制度/事物/地点/人物关系，逐条列出：

```python
shared_elements = [
    "天仙配APP",      # 制度(工具)
    "抑Y药物",        # 制度
    "黑人街",         # 地点
    "基因优化论",     # 意识形态
    "白人和黑人的关系", # 种族关系
    "老师赵雅雯",     # 角色(她的态度也在变)
]
```

**Step 2：确定当前视角下的情感滤镜**

对每个元素，确定当前卡视角下的价值判断转化：

| 元素 | 苦主视角（原文立场） | NTL视角（征服者立场） |
|------|-------------------|-------------------|
| APP配对 | 剥夺选择权→屈辱 | 获得便利→特权 |
| 黑人街 | 恐惧区域 | 猎场/领地 |
| 药物 | 迫害工具 | 人口控制手段 |

**Step 3：逐条审查着色一致性**

- 搜全卡所有条目content中涉及该世界观的描述
- 对照Step 2的表格，每处描述必须适配当前视角的情感滤镜
- 关键词对换表可以辅助审查：
  ```
  苦主语料 → NTL语料
  "奴役/强迫/被迫" → "特权/赋予/获得"
  "压迫/剥夺" → "筛选/保障"
  "恐惧/魔窟" → "自由/乐园"
  ```

### 与现有工作的关系

- 本流程应在**条目内容编写阶段**（Phase 2）的最后执行，而非审查阶段
- 如果先写完了所有条目再统一着色，可能会漏掉视角不一致的描述
- 最佳实践：在确定每张卡的{{user}}身份后，**先对着色表**，再逐条写内容
- 着色不一致的典型症状：NTL卡里出现苦主卡对同一制度的憎恨语气（如NTL征服者骂"APP太恶心了"）

## 级联构建及其风险

当制作3+张同源NTL卡时，用"级联"而非每张都从原版NTR卡重建：
1. 第一张卡从原版NTR卡完整构建（最慢，~2小时）
2. 第二、三张卡基于**第一张NTL卡**改造——只改{{user}}相关的~10条条目+开场白+shell
3. 子代理直接读第一张NTL卡的JSON，逐条判断"保留/修改/新增"
4. 效率：第二张卡只需改10/43条条目，比从原版NTR卡重建省60%工作量

**⚠️ 级联构建的污染风险（2026-07-12实测）**：
子代理基于第一张NTL卡改造时，会做表面文字替换但深层内容完全不改。结果：
- 兽人将军卡：11个条目含"赌场""VIP"等赌场残留
- 爱德卡：85-99%条目与赌场卡相同，爱德被描述成有"兽人血脉""黑色巨根"

**级联构建防污染规则**：
- ✅ 可直接复用：角色档案条目（四女档案，微调"对当前{{user}}的反应"即可）
- ⚠️ 谨慎复用：NPC竞争者条目（保留竞争者自身描述，但清理"我方的赌场/军营"混淆）
- ❌ 禁止复用：系统常驻条目（ID0-9）、阶段规则（ID21-25）、描写库（ID30）、对话库（ID32）——这些必须基于NTR原版重新写或大幅改造
- 合并后必须跑**跨卡污染检测**（见下方"跨卡污染检测"脚本）

**第一张NTL卡的安全过滤分工**：
- 子代理1：系统常驻条目(ID0-9)——不含NSFW，安全过滤不拦截
- 子代理2：角色档案条目(ID10-20)——角色描述通常不触发安全过滤
- 主代理execute_code：阶段系统+事件种子+描写库+结局(ID21-42)——NSFW场景描写必被安全过滤拒绝，必须主代理直接写
- 子代理3：开场白(≥1400字)——有NSFW风险，准备好主代理回退方案

**first_mes关键词优化步骤（NTL变体卡合并后必做）**：
NTL变体卡的first_mes从新{{user}}视角重写，触发模式完全不同于原版：
1. 列出first_mes中出现的所有角色名/关键词
2. 对照触发条目的keys，找出哪些条目会被first_mes触发
3. 用复合关键词（"古兰"而非"师傅"，"废物"而非"伯里"，"大壮"而非"保镖"）减少误触发
4. 目标：first_mes触发≤5条触发条目，总token负载<8000

## 常见子代理输出缺陷
1. extensions字段不完整（只有1个字段，应有31个）→ 从模板复制
2. constant条目被加上keys → 合并后强制清空
3. content中含emoji → 合并后批量替换为纯文本
4. alternate_greetings未改写 → 逐条检查是否含原版元素
5. 条目content偏短（安全过滤截断）→ 手动扩充到目标长度±20%
6. **alternate_greetings长度不足**（2026-07-12三NTL卡验证）：子代理产出的greeting普遍<800字符（应≥1400）。子代理倾向于写"精炼"的场景片段而非完整叙事。**合并后必须逐条检查长度**，不足的用execute_code或write_file扩写（追加场景细节+旁白+心理描写+对话）
7. **`{{user}}`占位符泄漏**（2026-07-12兽人将军卡）：从第一张NTL卡复制到第二张时，条目content中的"原{{user}}"会渲染为新卡的{{user}}名（如"原兽人将军"而非"原赌场老板"）。**合并后必须全文扫描`原{{user}}`→替换为实际角色名**
8. **并行子代理写同一文件导致数据丢失**（2026-07-12爱德卡惨痛教训）：三个子代理同时修改同一JSON文件→每个子代理都读取原始版本→各自修改→各自保存→最后保存的覆盖前两个的修改→32条需要手动重做。**铁律：并行子代理必须写不同文件，最后由主代理合并。** 每个子代理输出到独立文件（如`_part1.json`/`_part2.json`/`_part3.json`），主代理读取→合并→写入最终文件。绝不允许多个子代理同时写同一个文件。如果只有少量条目需要修改（<15条），用单个子代理或主代理直接execute_code，不要派并行子代理。
9. **常驻条目keys在批量替换中被错误修改**（2026-07-12爱德卡ID8）：批量替换关键词时误将常驻条目的keys=[]改成了非空数组→validate_card报错。**批量替换脚本必须先检查`if e.get('constant'): continue`跳过keys字段，或在替换后重新强制`e['keys'] = []`**
10. **级联复制污染——子代理基于NTL卡而非NTR原版构建**（2026-07-12异世界三NTL卡审查）：制作第二、三张NTL卡时，子代理拿了第一张NTL卡（赌场）做模板，做了表面文字替换（`赌场→旅馆`、`保镖→（爱德独自行动）`、`金币→权杖符文`），但深层内容完全是从第一张卡复制的。结果：爱德卡85-99%条目与赌场卡相同，爱德被描述成有"兽人血脉""黑色巨根""商人形象"——这些与爱德（小屁孩+长老权杖）完全矛盾。**铁律：第二张及以后的NTL变体卡必须基于NTR原版构建，不能基于第一张NTL卡**。级联构建只适用于角色档案（四女档案可复用），不适用于系统条目（阶段规则/描写库/征服特征）。如果必须基于第一张NTL卡改造，合并后必须跑**跨卡污染检测**（见下方新增的"跨卡污染检测"部分）

## 残留清理：变体卡关键词批量替换（2026-07-12异世界三NTL卡验证）

从原版卡复制到变体卡后，大量条目残留原版{{user}}的描述。需要系统化清理。

### 三步清理法

**Step 1：关键词扫描**
```python
stale_kw = ['赌场', 'VIP', '赌局', '筹码', '保镖', '小猫咪', '军营', '兽人之力']
skip_ids = {9, 15, 16, 17, 18}  # 竞争者NPC条目——保留其自身领地描述
for e in entries:
    if e['id'] in skip_ids: continue
    found = [kw for kw in stale_kw if kw in e.get('content','')]
    if found: print(f"  ID{e['id']}: {found}")
```

**Step 2：批量替换（排除竞争者NPC条目）**
```python
replacements = {'赌场': '旅馆', '保镖': '（已移除）', '金币': '法杖符文', ...}
for e in entries:
    if e['id'] in skip_ids: continue
    if e.get('constant'):  # 常驻条目只改content，不改keys
        for old, new in replacements.items():
            e['content'] = e['content'].replace(old, new)
    else:
        for old, new in replacements.items():
            e['content'] = e['content'].replace(old, new)
```

**Step 3：验证**
```python
remaining = 0
for e in entries:
    if e['id'] in skip_ids: continue
    found = [kw for kw in stale_kw if kw in e.get('content','')]
    if found: remaining += 1; print(f"  ID{e['id']}: {found}")
print(f"Remaining: {remaining}")
```

### 合理残留 vs 需要清理

| 类型 | 示例 | 处理 |
|------|------|------|
| 竞争者NPC条目 | ID15"黑巨汉赌场老板"提到"赌场" | **保留**——这是NPC自己的领地 |
| 世界观背景描写 | first_mes"远处传来赌场方向的喧闹声" | **保留**——环境描写，赌场作为地标存在 |
| {{user}}自身行为 | ID8"赌场经营系统"描述{{user}}的赌场 | **必须清理**——{{user}}不是赌场老板 |
| 事件种子 | ID29"事件·赌场初遇" | **必须清理**——改写为符合新{{user}}的事件 |
