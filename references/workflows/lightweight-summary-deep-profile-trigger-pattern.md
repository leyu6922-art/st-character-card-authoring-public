# 自然触发主档案 / 中厚速览触发模式

> 来源：校园示例卡婊子记·守护卡 v2 反思修复（2026-07-15）。旧版“轻量速览 + `角色名档案` 深度档案”会产生死 key：AI/玩家正常对话几乎不会说“雪乃档案”这种词，导致深度档案长期不用。本文件替代旧规则。

## 核心结论

1. **高 token 本身不是错误**。大型结构化卡等大型卡实测可在 10w 级上下文下顺畅生成。触发负载应作为诊断指标，而不是硬性失败阈值。
2. 真正需要修的是：泛 key 误触发、无关条目污染、递归触发链、上下文截断、模型实际变慢/变差。
3. `雪乃档案`、`结衣档案` 这类专用 key 如果不会自然出现在 chat history 中，就是死 key。不要为了降 token 设计不可触发条目。
4. ST 不递归扫描已插入的世界书条目；`prevent_recursion=true` 时更不可能通过“速览里写了档案 key”自动触发深度档案。

## 推荐方案 A：自然角色名直接触发主档案（默认）

适用：模型/预设上下文足够，首轮加载 1w-10w token 仍能正常生成。

| 层级 | key策略 | opening是否触发 | 说明 |
|---|---|---|---|
| 主档案 | 自然角色名/常用称呼：`雪乃`、`结衣`、`户部` | 是 | 让 AI 在角色出现时直接拿到完整行为链/语言指纹/风险信号 |
| 场景/事件 | 自然场景词：`KTV包间`、`比企谷家`、`五楼空教室` | 是/按场景 | 与角色档案共同加载 |
| 冷门后台条目 | 自然但低频词：`材木座`、`小丹尼`、`体育教师值班室` | 按需 | 不用“档案”后缀强迫触发 |

### 构建规则

- 角色/威胁档案保持 1500-2500 中文字。
- keys 使用玩家或 AI 会自然说出的名字/称呼。
- 不用 `角色名档案` 作为唯一 key；可以作为备用 key，但不能依赖它。
- opening 触发多个深度档案是可接受的，只要内容都与场景相关。
- validate/audit 中的高 token 负载只作为诊断项：检查是否有泛 key、无关条目、截断或模型质量下降。

## 方案 B：中厚速览 + 主档案自然触发（低上下文模型备用）

适用：用户明确使用小上下文模型、ST 实测截断，或首轮加载大量无关角色导致质量下降。

与旧版不同：中厚速览不是目录，也不能依赖“档案 key”自动触发。

- 中厚速览：250-350 中文字，自然角色名触发，本身必须可用。
- 主档案：仍然应该有自然触发路径；可以用更精确的自然组合 key（如 `雪乃` + `KTV` 的 selective 范围绑定），不要只用 `雪乃档案`。
- 如果主档案不希望首轮触发，用 selective + secondary 绑定**自然场景/阶段词**，而不是人工档案词。

中厚速览必须包含：

1. 身份/关系；
2. 当前风险信号；
3. 守护或威胁判断点；
4. 当前回合写法；
5. 可介入窗口。

## 方案 C：场景绑定自然触发（精确但不死 key）

适用：角色很多，但某些档案只应在特定场景加载。

示例：

```json
{
  "keys": ["雪乃", "雪之下"],
  "selective": true,
  "secondary_keys": ["KTV", "侍奉部", "五楼空教室", "更衣室"],
  "selectiveLogic": 0
}
```

含义：文本里出现雪乃，且同时出现自然场景词时加载。这样仍然依赖真实对话，而不是人工“雪乃档案”。

## Token/字符判断校准

SillyTavern 历史请求查看器或原始请求里的“10万”经常是**字符数/JSON请求体规模**，不是一次真实消耗 10万 input tokens。一次请求会重新组装完整上下文（预设、角色卡、世界书、作者注、聊天记录、扩展注入等），所以字符数看起来很大很正常。

判断顺序：

1. 先看 ST 的 **Prompt Itemization / 提示词明细**，确认占用来自角色卡、世界书、聊天历史还是预设。
2. 再看 API 返回的 `prompt_tokens/input_tokens`（若渠道提供）或模型官方 countTokens。
3. 不要把 validate/audit 的字符折算值当作计费 token 或模型硬上限。
4. 长上下文真正的风险是**每轮重复计费**与上下文污染，不是“单轮看到 10万字符”。
5. 如果模型上下文足够（如 Gemini 百万级上下文）且实际输出顺畅，可以接受大型世界书自然加载。

## 验证标准

必须同时看两类结果：

### 1. 触发可达性

- 核心角色在实际 greeting / chat 中能自然触发主内容；
- 没有只能靠 `角色名档案` 触发的死条目；
- 如果条目“所有开场白均不触发”，必须确认它是后期冷门条目，而不是核心角色档案。

### 2. 触发质量

- 高 token ≠ 错误；
- 泛 key、单字 key、普通句误触发才是硬问题；
- 如果 10w token 仍顺畅且内容相关，不必为降 token 牺牲内容可用性；
- 如果高 token 来自无关角色/重复条目/递归链，必须修。

推荐命令：

```bash
python scripts/validate_card.py <card.json>
python scripts/audit_worldbook_triggers.py <card.json> -o <report.md>
python scripts/enrichment_self_check.py <card.json>
```

## 常见坑

### 1. 用“档案后缀”制造死 key

错误：`keys=["雪乃档案", "雪之下雪乃档案"]`，opening 中只有“雪乃”。

结果：深度档案永远不触发，AI只拿到薄速览。

修复：`keys=["雪乃", "雪之下", "雪之下雪乃"]`，让角色出现时直接加载主档案；必要时用自然场景词 selective 限定。

### 2. 速览太薄

错误：速览 90-130 中文字，只写“需要深度素材时触发雪乃档案”。

结果：由于 ST 不递归扫描已插入条目，深度档案不会自动加载，速览又不足以写戏。

修复：要么自然名直接触发主档案；要么中厚速览本身自足。

### 3. 把 token 预算当硬红线

错误：validate/audit 报 8000+ tokens 就强行把自然 key 改成死 key。

结果：token 降了，但内容不可用。

修复：先确认 ST/模型是否真的截断或质量下降。若没有，保留高质量自然触发。只清理误触发和无关污染。

### 4. 新增条目 extensions 不完整

新增条目时从空扩展模板复制，导致缺 31 字段。

修复：从现有完整条目复制 extensions，并立即跑 validate_card.py。

## 适用案例

校园示例卡婊子记·守护卡 v2 修复后：

- 删除“角色速览”重复层；
- 角色/威胁主档案改回自然角色名触发；
- 首轮负载约 8k-11k tokens，但内容相关；
- validate_card.py 通过，token 负载仅作为诊断 warning，不再阻断交付。
