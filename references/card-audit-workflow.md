# 角色卡审查工作流（脚本审查 + Agent审查）

## 触发条件
用户说"审查/审卡/audit/review 角色卡"时使用此流程。

## Phase 1: 脚本审查（自动化检查）

用 `execute_code` 跑以下检查项：

### P0 — 结构一致性
- `顶层first_mes` vs `data.first_mes` 长度/内容是否一致
- `顶层name` vs `data.name` 是否一致
- 有无 `originalData` 格式（旧版ST需要）

### P1 — 条目质量
- 条目内容长度分布（平均值、最短条目）
- `constant=True` 但 `position=after_char` 的条目（可能应改before_char）
- 无key且非常驻的"死条目"（永远不会被触发）
- 关键词重复统计（同一条消息触发多条目 = token浪费）
- `system_prompt` 长度（与规划书对比）
- `description` 长度
- `mes_example` 是否为空
- `alternate_greetings` 数量和长度

### P2 — 内容安全
- emoji/Unicode转义检查（`[U+xxxx]` 或 `\\u` 格式会被ST原样输出）
- 违禁词扫描（萝莉/幼女/童贞等类脑社区禁词）

### P3 — 规划书对照
- 读规划书，对比条目数量、每条预估字数 vs 实际
- 对比角色覆盖完整性

## Phase 2: Agent审查（内容质量）

### 抽样读取
- 系统条目(0-6) 全读
- 角色条目(7-19) 抽样3-5个（核心角色优先）
- 对话精华库全读
- 功能条目抽样2-3个
- first_mes + alternate_greetings 抽样2个

### 评估维度
1. **具体可用内容比例** — 行为模板vs抽象规则？对话是原著摘录还是编造？
2. **角色区分度** — 每个角色是否有独特的语言风格/行为模板？
3. **堕落阶段覆盖** — 每个角色是否有明确的阶段转换逻辑？
4. **五感描写** — 性爱场景是否有具体感官描写而非笼统描述？
5. **对话库质量** — 是否有分阶段对话？是否标注了触发场景？
6. **OOC防护** — 是否有"不会说的话/做的事"负面清单？
7. **跨条目联动** — 条目间是否互相引用？有无孤立条目？

### 输出格式
```
基础数据: 文件大小/条目数/内容字数/开场白数
脚本审查: 按P0-P3分级列出问题
Agent审查: 按条目评分 + 关键发现
总结: 需修/建议修/可选 三级
```

## Pitfalls
1. **validate_card.py 可能返回空输出** — 该脚本exit 0但无stdout时，说明脚本内部异常被吞掉了。不要依赖它的输出作为唯一审查手段，必须用execute_code自建检查。
2. **文件大小 ≠ 内容大小** — JSON格式化空白可能占50%以上（如254KB文件实际内容114KB）。用json.dumps算真实大小。
3. **constant+after_char 不一定是bug** — 世界观/文风/旁白条目放after_char是合理选择（在角色描述之后补充上下文）。但防拒绝/格式规则建议放before_char。
4. **关键词重复不一定是问题** — 角色条目和功能条目共享"辣妹""场景"等词是正常的。重点看是否导致同一条消息触发5+条目。
5. **规划书字数预估通常偏高** — 实际条目内容往往是预估的60-70%，这是正常的（规划书是理想值）。
