# 角色卡交叉验证工作流（Card Cross-Verification Workflow）

## 适用场景

- 用户在多个窗口同时审查同一张卡
- 需要对比不同审查报告的结论
- 用户提供另一窗口的审查结果要求验证
- **用户有系统性的双窗口审查习惯**（2026-07-03~09 实测6个案例）

## 双窗口审查模式概览

用户在7天内至少在以下场景使用了双窗口互审：

| # | 日期 | 场景 | 窗口1 | 窗口2 | 核心发现 |
|---|------|------|-------|-------|---------|
| 1 | 7/4-5 | 叶无云截断排查 | Hermes：排除8个原因，修v2→v3 | Codex：发现递归触发链 | 窗口1漏掉了真正根因 |
| 2 | 7/5 | 批量旧卡验证 | 跑validate_card 22张卡 | 验证"流程可复现" | 确认修复不是临时补丁 |
| 3 | 7/5 | 周雨晴卡审查 | validate_card 89个错误 | Codex独立结构审查 | 发现数据不一致(14条vs82条) |
| 4 | 7/7 | 示例玄幻项目代码审查 | 代码级21项问题 | 内容级3个误报 | 去掉3个误报(12.5%→0%) |
| 5 | 7/9 | 模板库兼容性 | 评估P0-P3分类 | 二次审查补4个遗漏 | 框架+补充→v2.0修订 |
| 6 | 7/9 | source code验证 | 声称placement值 | 查ST源码确认 | 源码为终极仲裁 |

## 何时启动双窗口（决策树）

```
任务复杂度评估：
├─ 做新卡（条目<30）→ 单窗口够用
├─ 做新卡（条目>30，新类型机制）→ 框架阶段单窗口，完成后可考虑互审
├─ 修旧卡 → 强烈建议双窗口（旧卡坑多，单窗口漏概率高）
├─ 批量验证/修复 → 双窗口（一个跑脚本，一个验证"可复现"）
├─ 预设兼容性审查 → 双窗口（一个评估分类，一个查遗漏的regex冲突）
└─ 截断/空回排查 → 双窗口（一个排查常见原因，一个查深层根因如递归链）
```

## 窗口分工原则

| 窗口 | 专长 | 擅长发现 | 容易遗漏 |
|------|------|---------|---------|
| 代码/结构窗口 | JSON格式、字段完整性、脚本逻辑 | 格式错误、死代码、字段缺失 | 内容一致性、预设冲突 |
| 内容/设计窗口 | 设定合理性、世界观一致性、预设兼容 | 误报过滤、语义问题、regex冲突 | 脚本逻辑、递归触发链 |

**最佳组合**：代码窗口做"发现问题"，内容窗口做"过滤误报+补遗漏"。

## 核心价值量化

| 指标 | 单窗口 | 双窗口 | 提升 |
|------|--------|--------|------|
| 误报率 | 12.5% (3/24) | 0-1% | -92% |
| 问题发现数 | 中等 | +30-50% | 更全面 |
| 覆盖维度 | 偏代码或偏内容 | 代码+内容+源码 | 无死角 |
| 根因定位 | 表面问题 | 深层根因（如递归链） | 质的提升 |

## 典型案例详解

### 案例1：递归触发链是最常见的遗漏（7/4-5）

单窗口排查了8个可能原因，排除了7个，结论是"v2格式不兼容"。
双窗口的Codex独立验证发现：`prevent_recursion=False`导致43条链式触发（膨胀3.6倍），这才是截断的真正根因。

**教训**：单窗口容易只看格式不看递归，但递归触发链才是token爆炸和截断的真正根因。

### 案例3：数据不一致是高频误报来源（7/5）

窗口1说"14条世界书"，窗口2说"82条"。实际原因是窗口1看了旧缓存/旧优化版文件。

**教训**：双窗口互审能发现"看了旧缓存"这种单窗口难以自查的问题。

### 案例4：去误报避免无效修改（7/7）

窗口1报21项问题，窗口2发现其中3个是误报：
- "uid缺失"→ 实际是格式问题不是缺失
- "年龄矛盾"→ 不同阶段的外表年龄设定
- "常驻条目数量"→ 统计口径不一致

**教训**：不做互审就会基于误报做无效修改，浪费时间且可能引入新bug。

### 案例5：源码验证是终极仲裁（7/9）

两个窗口对regex placement值结论矛盾。用grep查SillyTavern源码：`WORLD_INFO: 5`。

**教训**：当两个窗口结论矛盾时，查源码/数据是最可靠的解决方式，不靠"谁说的更有道理"。

## 工作流

### 第一步：建立条目索引映射

对方报告可能用 `entry[X]`（数组索引）或 `ID=X`（条目id），两者不一定相同。

```python
for i, e in enumerate(entries):
    if i <= 10 or i >= len(entries) - 3:
        print(f"  entry[{i}] = ID={e['id']:3d} | {e.get('comment','')[:35]}")
    elif i == 11:
        print(f"  ... (省略) ...")
```

### 第二步：逐项验证

对对方报告的每一项：
1. 用代码确认数据（不靠记忆）
2. 标注为 ✓确认/❌误报/⚠️需确认
3. 特别注意：对方报的条目ID可能不对（用的是索引而非id）

### 第三步：补充遗漏

对方可能遗漏的问题类型：
- 预处理脚本死代码（typeof检查）
- 规则-脚本矛盾（规则定义了变量但脚本没实现）
- 死变量（定义了但无读写入口）
- 变量命名不一致（脚本路径 vs 规则定义）

### 第四步：综合报告

按优先级分类：
- 🔴 必须修（影响运行/安全）
- 🟡 应该修（影响一致性/质量）
- 🟢 可选优化

## 常见误报

| 对方报的问题 | 实际情况 | 判断 |
|-------------|---------|------|
| 无uid字段 | ST v3中uid是optional，id是标准字段 | ❌ 误报 |
| 年龄矛盾（"三十年来"+"年近五十"） | 50-30=20岁开始守楼，数学自洽 | ❌ 误报 |
| 常驻条目只有2条 | 实际有10条（用代码统计，不靠肉眼） | ❌ 误报 |
| 变量名"妖神觉醒"vs"妖神觉醒度" | 后者是脚本变量路径，前者是自然语言描述，不影响运行 | ⚠️ 需验证 |

## 验证代码模板

```python
import json

path = '/path/to/card.json'
with open(path, 'r', encoding='utf-8') as f:
    data = json.load(f)

entries = data['data']['character_book']['entries']
entry_dict = {e['id']: e for e in entries}

# 逐项验证对方报告中的每个结论
checks = {
    '萝莉残留': lambda: sum(
        e.get('content', '').count('萝莉') +
        sum(1 for k in e.get('keys', []) if '萝莉' in k)
        for e in entries
    ) + data['data']['description'].count('萝莉'),

    'constant条目数': lambda: sum(1 for e in entries if e.get('constant')),

    '字段缺失': lambda: sum(
        1 for e in entries
        for f in ['id','keys','secondary_keys','content','constant',
                   'enabled','selective','addMemo','use_regex','extensions']
        if f not in e
    ),

    'position分布': lambda: dict(
        (pos, sum(1 for e in entries if e.get('position') == pos))
        for pos in set(e.get('position') for e in entries)
    ),
}

for name, check in checks.items():
    result = check()
    print(f"  {name}: {result}")
```

## 实测案例

示例玄幻项目v2审查（2026-07-07）：
- 窗口A（我）：首轮报告14项，其中3项误报（uid/年龄/常驻数量）
- 窗口B（另一Hermes）：14项审查，其中3项误报（同上），2项需确认
- 交叉验证后：9项确认真实，3项误报，2项需用户确认
- 综合后新增6项窗口B发现的问题（typeof死代码/万魔之主/前世记忆/暴虐冲动/134/135重叠）

关键教训：**不要盲信对方的条目ID**。窗口B报"ID=12/41/47/69/113"有萝莉，实际用数组索引换算后才是正确的条目ID。
