# 开放兼容型模块化语义档案架构

## 适用范围

当小说角色卡需要同时满足以下条件时使用本模式：

- 角色和世界观要有原文锚点，但不要求逐章复播；
- 玩家可以改写关系顺序、介入方式、事件时间和结局；
- 角色仍需保持稳定的身份、人格、语言、行为逻辑；
- 卡片可能运行在 `flat`、`native_stage` 或 MVU/EJS 环境；
- 需要让模型读懂“这一条负责什么”，而不是只看见一个大块角色档案。

本模式优化的是**内容建模层**，不是单独的脚本机制。它可以和 `open_sandbox`、`soft_stage`、`linear_stage` 任一运行架构组合。

---

## 1. 第一性原理：开放不是取消约束

角色卡的真实目标不是“尽量还原小说”，也不是“让 AI 随便发挥”，而是：

```text
在稳定人物约束下，最大化玩家可探索的有效路线空间。
```

角色生成可以抽象成：

```text
当前状态 + 可见信息 + 场景刺激 + 关系对象 + 稳定人格
        ↓
角色的若干可接受响应
        ↓
玩家选择和 NPC 后果共同改变后续状态
```

错误架构通常是把它写成：

```text
原著第 N 章 → 固定事件 → 固定反应 → 下一章
```

或者反过来写成：

```text
AI 参考人物设定，自由发挥
```

前者把互动卡变成复播脚本，后者没有足够的行为约束，角色会漂移。

### TOC 约束诊断

开放兼容卡最主要的约束通常不是内容量，而是：

> **内容没有声明哪些东西可以变、哪些东西不能变、哪些东西只是候选。**

因果链：

```text
事实/推演/路线混写
→ 模型无法判断信息的稳定性
→ 原著事件被误当成必然历史，或设计内容被误当成事实
→ 玩家改写路线时出现设定冲突
→ Agent 只能用更多规则和更长条目补洞
→ Token 增长，但开放性和清晰度没有同步增长
```

因此第一优先级不是继续加字数，而是先建立**锚点—可变性—运行时**三层合同。

## 2. 两轴标注：来源状态和可变性不能混为一谈

分析层和 build manifest 必须为每个关键设定记录两种属性。它们可以出现在工程源文件中，但默认不进入模型可见正文。

### 2.1 来源状态 `evidence_status`

| 值 | 含义 | 处理方式 |
|---|---|---|
| `F` | 原文直接事实或可精确回查引文 | 可写入事实锚点 |
| `I` | 基于多处原文的高可信归纳 | 写成稳定倾向，不伪装成原句 |
| `D` | 本卡为开放玩法做出的设计 | 写成可能性/候选，不冒充原著历史 |
| `U` | 原文未确认、存在矛盾或空白 | 保留未知，不自动补死 |

### 2.2 可变性 `mutability`

| 值 | 含义 | 例子 |
|---|---|---|
| `H` | 硬锚点：正常开放路线不能悄悄改变 | 身份、确定血缘、已确认核心关系、世界基本规则 |
| `S` | 软锚点：保持倾向，但可换场景和表达 | 习惯、职业表现、常见防御方式、关系中的惯常姿态 |
| `O` | 开放槽位：由玩家、当前情境或设计分支决定 | 事件顺序、关系推进速度、具体地点、支线对象、结局 |
| `R` | 运行时字段：只属于加载和路由 | key、enabled、阶段装载、变量、扫描深度 |

### 2.3 组合判断

- `F + H`：事实硬锚点，不能被普通开放事件改写；
- `F + S`：事实存在，但可重组表现方式；
- `F + O`：原文提供过可能性，但当前卡不把它锁为必经路线；
- `I + H`：危险组合。高可信推断不能未经用户决策直接硬化为不可变事实；
- `D + H`：可以成为本卡规则，但必须记录为本卡设计，不得伪称原著；
- `U + O`：开放未知。模型可以提出候选，但不能把候选写成已经发生；
- 任意 `R`：不得混入角色事实或世界观正文。

### 2.4 关键原则

“开放兼容”不是把所有设定都标成 `O`。如果身份、血缘、称谓、基础世界规则都可以随意变，模型得到的不是开放世界，而是没有连续性的随机文本。

## 2.5 Semantic IR：在内容层与运行时之间增加中间层

两轴还不够支撑多运行时投影。启用新 profile 后，建议把语义源按以下最小中间表示组织；这些字段默认留在 manifest/分析层，不直接泄漏到模型可见正文。

### M0：项目与运行时总合同

```json
{
  "project_id": "example_open_card",
  "contract_level": "lite | standard | full",
  "source_scope": {"canonical_sources": [], "excluded_sources": [], "source_hashes": {}},
  "player_anchor": {"mode": "{{user}} | fixed_character | observer | selectable_identity", "entity_id": "player"},
  "narrative_mode": "source_default | open_sandbox | stage_progression",
  "architecture_mode": "flat | native_stage | mvu",
  "authoritative_route": "natural_keys | greeting_title | runtime.stage",
  "authoritative_state": "narrative_only | greeting_snapshot | stat_data",
  "runtime_capabilities": ["natural_trigger", "open_sandbox"]
}
```

硬规则：Greeting 标题、自然 key 和 `runtime.stage`不能同时作为无主状态源；必须声明一套权威路由，其他只能是辅助投影。

### 两份 manifest 的字段所有权

`build/semantic-module-manifest.json` 和项目根目录的 `build_manifest.json` 不是同一个文件，也不能互相替代：

| 字段 | 唯一权威文件 | 作用 |
|---|---|---|
| `semantic_profile`、`contract_level`、`source_scope`、`characters`、`world_modules`、`projections` | semantic manifest | 语义合同、来源/实体/模块和投影意图 |
| `schema_version`、`prototype`、`routing_mode`、`canonical_sources`、`runtime_driver`、`semantic_manifest` | `build_manifest.json` | 交付策略、真实 source/build 路径和门控编排 |
| `architecture_mode` | semantic manifest | 语义层目标投影：`flat`、`native_stage` 或 `mvu` |
| `routing_mode` | `build_manifest.json` | 当前 Runner 实际执行的 `flat`、`native_greeting_title` 或 `simple_stage_route` |

`architecture_mode` 不会自动改写 `routing_mode`；二者必须由项目合同明确对应。`source_scope.canonical_sources` 是语义来源记录，`build_manifest.canonical_sources` 才是 source coverage 门控输入；两者不一致时不能把其中一个当作另一个的自动同步结果。
### M1：实体注册表

实体注册表只回答“世界里有哪些人、物、地点、组织”，不负责详细行为、关系结局或秘密内容。每个实体至少有稳定 `entity_id`、规范名、别名、类型、来源引用和冲突记录。角色改名不能改变 `entity_id`；同名人物不能仅凭字符串自动合并。

### M2：事实/关系账本

关键事实至少区分：`source_kind`（原著事实/推断/卡内设计/当前观测）、`truth_status`（confirmed/inferred/candidate/unresolved）、`time_scope`（past/present/future）、`visibility`（model_visible/stage_scoped/build_only/forbidden_early）和`mutability`。这比单一“原文/非原文”标签更能防止未来事实提前泄漏，也能让关系改写有明确影响范围。

### M10：运行时投影映射

语义模块必须能声明如何投影，而不是直接依赖某一种 ST 条目结构：

```json
{
  "semantic_ref": "EVT-021",
  "runtime_role": "event_candidate",
  "flat": {"load": "selective", "natural_keys": []},
  "native_stage": {"pack": "event_pack", "stage": "P1", "route_key_source": "greeting_title"},
  "mvu": {"state_effects": [], "event_id_path": "continuity.active_events"}
}
```

因此，阶段包是运行时视图，不是语义唯一真相源；同一语义模块可以投影到 Flat、Native-Stage 或 MVU，而不要求角色正文知道 `keys`、变量路径或脚本实现。

### 三档复杂度

- **Lite**：项目合同、实体、事实/角色行为、场景、候选事件、运行时合同；适合简单 Flat 卡。
- **Standard**：Lite + 关系图、知识边界、阶段增量、证据 manifest；适合小说源驱动阶段卡。
- **Full**：Standard + 生命周期状态、事件效果、MVU/TH 合同和运行时模拟；只用于确实需要持久化状态的工程卡。

不要因为存在 `semantic_profile` 就强迫所有项目使用 Full；复杂度必须由运行时能力和一致性需求驱动。

## 3. 三层内容模型

### 3.1 世界框架层：固定可感知的舞台

定义：

- 时间和地点的基本关系；
- 社会规则、物理规则、组织规则；
- 可反复使用的空间、物件、制度和感官锚点；
- 不同地点能承载什么类型的互动。

世界框架可以开放扩展，但扩展必须遵守既有空间逻辑、社会后果和可见信息边界。

### 3.2 角色语义层：稳定但可表现为多种响应的人格

定义：

- 角色身份和关系锚点；
- 核心欲望、恐惧、价值冲突和防御机制；
- 语言、称谓、身体习惯、职业机制；
- 面对不同对象、地点和压力时的响应函数；
- 角色明确不知道什么、容易误判什么。

这里不写固定剧情顺序，而写“刺激出现时角色倾向如何表现”。

### 3.3 路线与情境层：开放的可选组合

定义：

- 候选事件；
- 自然切入点；
- 玩家接管窗口；
- 可以改写的关系顺序和场景组合；
- 可能产生的后果和分歧方向。

情境层可以参考原著，但不能把“候选”写成“已发生”，不能替玩家说话、决定、移动、同意、拒绝或完成关系跳变。

**核心分离：**

```text
世界框架 = 这个世界允许什么
角色语义 = 这个人遇到刺激通常如何反应
开放路线 = 这次故事选择把什么组合在一起
```

## 4. 条目拓扑：从“一角色一大档案”改为“对象 × 职责模块”

### 4.1 推荐命名空间

```text
角色/<角色名>/00_角色总解释
角色/<角色名>/01_基础信息与关系锚点
角色/<角色名>/02_外显与生活状态
角色/<角色名>/03_核心心理与性格
角色/<角色名>/04_行为响应与特质交叠
角色/<角色名>/05_语言与称谓
角色/<角色名>/06_关系网与情感动态
角色/<角色名>/07_场景物件与职业机制
角色/<角色名>/08_信息边界与误写红线
角色/<角色名>/P0_当前窗口表演

世界观/00_总设定
世界观/01_时间制度与动线
世界观/地点/<地点名>
世界观/组织/<组织名>
世界观/规则/<规则名>
世界观/开放扩展槽位
```

`P0` 只是工程层和目录层的阶段标识。若使用 `open_sandbox`，正文不能把 `P0` 写成必须经过的剧情顺序；若使用 `native_stage`，阶段条目仍然只是当前窗口内容，不得把所有候选事件写成已发生事实。

### 4.2 角色深度分级

不要求每个配角都拥有完整模块包：

| 角色级别 | 必需模块 | 用途 |
|---|---|---|
| `core` | 身份、心理、行为、语言、关系、场景、边界/开放 | 主视角和核心 NPC |
| `supporting` | 身份、行为/语言、关系或场景、边界 | 有独立目标的配角 |
| `ambient` | 身份/功能、出场条件、边界 | 仅承担环境和事件功能的 NPC |

这是质量分层，不是偷减内容。高质量卡应把有限写作资源集中到会改变玩家决策的角色。

## 5. 纯文本模块合同

每个角色或地点模块都必须回答以下问题。不要为了形式把所有字段写成空标题；字段没有内容时应在 manifest 中标记 `not_applicable`，而不是写抽象套话。

### 5.1 通用字段

```text
条目作用:
  本条回答什么问题；不回答什么问题。

核心锚点:
  稳定身份、关系、目标、习惯或空间事实。

具体表现:
  可观察的动作、表情、语言、选择、环境变化。

触发条件与响应:
  什么刺激出现时，角色如何解释、如何行动、可能如何说话。

交叠与冲突:
  两个特质、两个关系或两个目标同时出现时如何拉扯。

语言与称谓:
  对不同对象、不同压力和不同公开程度的说法差异。

信息边界:
  谁知道什么；角色不知道什么；什么只能作为玩家调查结果出现。

不应误写:
  具体禁止误读，不写泛泛的“保持人设”。

可开放变化:
  哪些时间、地点、顺序、对象、后果可以由玩家或情境改变。

关联模块:
  相关条目的真实 comment 路径；不得指向不存在的条目。
```

### 5.2 行为响应语法

优先使用以下链条，而不是形容词列表：

```text
外部刺激
→ 角色看到/听到什么
→ 角色如何解释
→ 微动作或身体反应
→ 说法/称谓/沉默
→ 下一步倾向
→ 对环境、关系或信息的影响
```

示例：

```text
触发条件:
  {{user}}在公开场合提到她过去不愿解释的关系。

可观察表现:
  她先把正在整理的物件放回原位，停顿时间比平常长；对旁人保持礼貌，只把称谓改得更正式；转入私下空间后才反问{{user}}想确认哪一部分。

可开放变化:
  {{user}}可以追问、转移话题、保护她或利用这次停顿；条目不规定唯一反应，也不自动揭露完整真相。
```

### 5.3 性格交叠

核心角色至少写出若干组真正会改变表现的交叠，而不是把特质重新排列：

```text
自由 × 温柔克制:
  她可能允许边界被试探，但会用日常动作维持关系表面的正常。

职业控制 × 私下依赖:
  她在公开场合先控制流程，私下才暴露对某个对象的依赖。
```

交叠项必须说明：

- 同时触发的条件；
- 哪个特质暂时占上风；
- 表现如何变化；
- 玩家怎样改变结果。

### 5.4 角色总解释的边界

`00_角色总解释`只写该角色专属的：

- 核心矛盾；
- 最容易被模型误读的地方；
- 稳定锚点和开放空间的区别；
- 各模块之间的调用关系。

通用运行规则、玩家代理权、导演协议、素材调用规则必须抽成全局常驻条目，不能在每个角色档案重复。

## 6. 世界观地点模块合同

每个重要地点使用以下结构：

```text
地点定位:
  这个地点在世界和叙事中的作用。

启用时间与可达性:
  什么时候可以自然到达；谁会主动出现；哪些阶段只是背景。

空间布局:
  入口、可见区域、私密区域、声音和视线关系。

常驻人物与活动:
  谁通常在这里做什么；谁只是偶然出现。

现实规则:
  门禁、营业、校园、组织、交通、社会礼仪等可观察规则。

感官锚点:
  光线、声音、气味、温度、物件和可重复动作。

场景边界:
  什么事情在这里自然，什么事情需要额外前提。

剧情功能:
  适合承载调查、谈判、日常、冲突、亲密或后果收束中的哪些部分。

自然入口:
  普通聊天中可能出现的地点名、物件、行动和人物组合。

可开放变化:
  玩家可以改变什么；改变后会留下什么现实后果。
```

地点不是背景百科。一个地点如果没有布局、规则、可见人物和自然入口，模型仍然不会把它当成可使用的空间。

## 7. 开放兼容合同

### 7.1 默认可开放的内容

在 `narrative_mode=open_sandbox` 且 `route_policy=player_led` 时，默认允许开放：

- 事件发生的时间和顺序；
- 角色之间的接近、疏远、合作和对抗方式；
- 玩家选择调查、保护、谈判、拒绝、离开或改写方向；
- 场景的组合和自然切入；
- 侧角色的出场顺序和局部目标；
- 原著空白处的对话、动作和后果；
- 候选事件的成功、失败、半成功和中断结果。

### 7.2 不得静默改变的内容

以下内容除非进入显式 variant contract，不得被普通开放情境悄悄改写：

- 核心身份和确定血缘；
- 已确认的基础关系；
- 世界的基本规则；
- 用户明确锁定的玩家身份；
- 用户明确锁定的成人化、时间线或视角范围；
- 角色的核心语言/人格锚点；
- 角色已经知道或明确不知道的信息边界。

如果用户要求改变这些内容，创建独立变体：

```yaml
variant_id: alternate_route_a
scope: relationship_and_timeline
changes:
  - relationship_anchor_x
  - opening_state_y
does_not_change:
  - character_voice
  - core_world_rules
affected_modules:
  - 角色/甲/01_基础信息与关系锚点
  - 角色/甲/06_关系网与情感动态
  - 世界观/01_时间制度与动线
```

不要把原版和变体事实并排塞进同一条常驻档案，让模型自行猜哪个是真的。

### 7.3 候选事件的语言

开放事件必须写成：

```text
当……出现时，可以从……自然进入。
角色可能……，但也可能……。
玩家可以选择……、……或……。
不同选择可能造成……、……或关系暂时停滞。
这只是可调用情境，不代表事件已经发生。
```

禁止把开放事件写成：

```text
事件必然发生。
AI自动触发。
角色必须进入下一阶段。
无论玩家怎么做都会成功/失败。
这是原著后续已经发生的事实。
```

如果这些内容属于世界的硬规则，应放到世界规则模块，不要伪装成开放事件。

## 8. 与运行时架构的关系

语义模块和运行时架构是两个正交维度：

```text
semantic_profile = modular_semantic_v1
narrative_mode   = open_sandbox | soft_stage | linear_stage
runtime_driver   = native_st | mvu | ejs
```

### flat / native_st

- 角色稳定模块使用自然角色名和自然场景词触发；
- 开放事件是 `candidate_pool`，不要通过人工 `P#` key 强锁路线；
- 没有脚本时，阶段只能是参考窗口或独立选择入口，不能假装有变量路由；
- 角色模块不应依赖递归触发自己或其他模块。

### native_stage

- Greeting 标题负责阶段装载，语义模块仍负责角色本体；
- 阶段模块只写当前窗口状态、可见信息和当前表现；
- 稳定角色模块不能泄漏后期关系、秘密和已改变的称谓；
- 阶段包是加载边界，不是自动剧情执行器。

### MVU/EJS

- 脚本只负责状态、开关和加载，不负责替代角色语义档案；
- 脚本入口、变量名、条目 comment 必须在 manifest 中登记；
- 纯文本模块不能反向依赖某个未接通的脚本变量；
- 必须同时保留无脚本降级说明，避免卡片脱离预设后变成空壳。

## 9. 生产流程

可直接复制 `templates/semantic-module-manifest.example.json` 作为起始 manifest，再按项目实际角色、地点和变体删改；不要把模板中的占位角色名当成真实设定。

1. **先定开放范围**：显式写 `narrative_mode`、`route_policy`、`event_mode`、`variant_id`。
2. **建立 canonical source manifest**：记录源文件、版本、章节/段落范围和 SHA；旧卡不是默认来源。
3. **建立锚点矩阵**：每个关键设定填写 `evidence_status`、`mutability`、拥有该设定的模块和变更影响范围。
4. **建立模块清单**：按角色深度分级决定哪些角色需要哪些模块；不要先写长档案再事后拆分。
5. **先写稳定模块**：身份、关系、心理、行为、语言、世界地点和信息边界。
6. **再写开放模块**：开放变化、候选事件、自然入口、玩家接管点和分支后果。
7. **最后接运行时**：keys、selective、enabled、阶段标题和变量只从 manifest/contract 生成。
8. **构建后审查**：模块完整性、锚点覆盖、跨条目引用、开放锁死词、未来泄漏、自然触发、token 负载和 build sync。
9. **只在必要时实机验证**：静态门控通过不等于 ST 已导入、触发和多轮表现都正确。

## 10. 自动门控要求

启用 `semantic_profile=modular_semantic_v1` 且在 `build_manifest.json` 声明 `semantic_manifest` 后，日常交付只运行统一入口：

```bash
python <card-skill>/scripts/run_delivery.py CARD.json --manifest build_manifest.json
```

`run_delivery.py` 会在 `final_delivery_gate.py` 前自动调用 `audit_semantic_modules.py`；语义 ERROR 返回 `exit 1`，语义 WARNING 至少返回 `exit 2`。直接调用语义脚本只用于失败诊断：

```bash
python <card-skill>/scripts/audit_semantic_modules.py CARD.json --manifest build/semantic-module-manifest.json
```

当前脚本实际检查：

- `角色/<name>/<facet>` 和 `世界观/<scope>/<name>` 命名空间唯一；
- manifest 声明的核心模块全部存在；
- 按模块类型检查条目作用、核心锚点、触发条件、具体表现、不应误写、可开放变化等必需字段；
- 跨条目引用指向实际 comment；
- `open_sandbox` 候选事件没有“自动触发、固定顺序、唯一结局”等硬锁表达；
- `runtime_clean` 模型可见层没有常见工程元数据残留；
- Standard/Full 项目合同、可见性和基础 projection 字段。

以下项目目前仍属于内容/运行时专项审查，不由该脚本单独证明：

- natural key 的真实触发可达性和泛词质量；
- 每个事实的 `evidence_status × mutability` 完整覆盖；
- projection 与最终 Flat/Native/MVU 条目的逐项回读；
- 未来关系/后期秘密的语义推理；
- SillyTavern 实际加载、触发和多轮行为。

字数、条目数量和原文引用数量只能作为 profile-specific 指标，不能替代模块语义完整性。

## 11. 优点与代价

### 优点

- 模型能按职责读取内容，减少一条大档案中的信息检索负担；
- 角色特质直接绑定触发条件和具体动作，不停留在性格标签；
- 原著锚点与开放路线分离，开放改写不必牺牲人物稳定性；
- 适合多角色、关系网和地点库持续扩展；
- 同一语义模块可以适配 flat、阶段卡和脚本运行时；
- 模块合同和负向门控可以自动发现“看似开放、实际锁死”的内容。

### 代价

- 条目数量可能增加，需要 manifest 和命名空间管理；
- 同一角色多个模块可能增加触发负载，需要 quick anchor、深度模块和自然 key 分层；
- 原文事实与开放设计必须做前置分类，不能一边写一边凭感觉混合；
- 自动门控只能检查结构和明显锁死词，不能替代人工判断人物是否真的自然；
- 若用户明确要求严格复播，开放模块必须缩窄，不能把开放默认值强行套到线性项目。

## 12. 新手最容易忽略的细节

1. “可以自由发挥”不是可执行合同；必须写出可变字段和不可变锚点。
2. `可能发生`如果放在“已经发生的章节事实”段落里，模型仍可能把它当成事实；候选事件要单独成条。
3. 只改 comment 不改 content 不会产生模块化；正文必须真的包含触发—表现—边界—开放变化。
4. 原文对白放在独立语料库不等于角色会用；应至少把少量高价值对白绑定到对应语言或行为模块。
5. 阶段变化应改变“当前表达和可见信息”，不能每个阶段重写一套互相矛盾的人格。
6. 关系变体必须同步更新关系矩阵、角色总解释、相关事件和 Greeting；不能只改一条关系条目。
7. `P0/P1`、`阶段包`、`素材库`是工程名称，不是自然触发词。
8. 地点重复事实要有单一来源和生成映射，否则总设定与地点条目迟早漂移。
9. `{{user}}`是否固定、是否可扮演角色，必须在 manifest 中先定；普通共用内容不要偷偷替玩家决定身份和行动。
10. “内容更长”不能证明结构更高级。优先增加可调用的行为差异、信息边界、关系后果和开放分支，而不是重复设定。

---

## 13. 质量判定

接近高质量生产标准的卡，不是“完全复刻原著”，也不是“完全自由创作”，而是同时满足：

```text
原文锚点可追溯
+ 稳定人格可执行
+ 开放变化有明确边界
+ 候选路线不冒充既定事实
+ 模块职责不重叠
+ 运行时加载与内容层分离
+ 结构有自动门控
```

缺任何一项，开放性都可能退化为“剧情锁死”或“人物漂移”。
