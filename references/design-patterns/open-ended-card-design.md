# 开放性卡片设计案例（示例玄幻项目改造）

## 背景

示例玄幻项目角色卡经历了从线性到开放的架构改造：
- 初始版本（v2.0）：68条目/281.5KB，线性事件驱动
- 扩充版本：133条目/603.8KB，合并后88条目/550.9KB
- 脚本化实装：伪代码→`<%_ _%>` JavaScript
- 开放性改造：从"按剧本演"改为"在沙盒中探索"

## 核心问题

原作是线性小说，但角色卡是互动游戏。将小说剧情翻译成if-else链会导致：
- 用户每一步踩在预设轨道上
- AI被强制按条件触发事件，丧失即兴创作能力
- 多周目可玩性极低

## 评审反馈的关键洞察

### 问题1：游戏机制 ≠ 剧本锁死

```
堕落度>=50触发阶段变化，本质上和HP降到0=死亡一样，是游戏规则。
不能说"HP降到0后AI自行判断角色是否死亡"——那HP就变成装饰品了。
```

### 问题2："追踪状态不追踪进度"是伪命题

```
堕落度从0→30→60→100，既是"当前状态"也是"剧情进度"。
真正的问题不是"变量在追踪进度"，而是"变量的阈值触发了什么"。
```

### 问题3：不能从一个极端走到另一个极端

```
之前质检报告写过："事件必须有明确的变量阈值判定，不能靠AI'自觉'触发。"
如果把所有条件都删掉，变成"AI参考世界观背景自行创作"，
等于和这句话直接矛盾。
```

## 中间路线方案

### 预处理脚本改造

| P级 | 线性 | 中间路线 |
|-----|------|----------|
| P0 灵魂崩溃 | 硬性触发 | 保留（游戏结束条件） |
| P1 噩梦升级 | 硬性触发 | 保留（世界观机制） |
| P2 相机进化 | 硬性触发 | 保留（物品机制） |
| P3 阶段跃迁 | 自动触发 | **阈值+提示** |
| P4 角色启动 | 自动触发 | **可选提示** |
| P5 风险检测 | 自动BAD END | **数值+警告** |
| P6 种子联动 | 自动触发 | **保留计算删触发** |

### 事件系统改造

5个事件（烛龙警告/批量腐蚀/前世觉醒/万魔之主/最终决战）从：
```
触发条件→自动执行→变量更新
```
改为：
```
世界观背景+触发参考+AI可选触发
```

每个事件条目增加"AI使用指南"。

### 变量系统

- 阶段变量（异变/堕落/觉醒/共生/归真）：**保留**
- 阈值从"充分条件"改为"必要条件"
- 天命事件标记（烛龙警告/批量腐蚀/最终决战）：**删除**

### Phase划分

从"强制解锁顺序"改为"推荐引入场景"：
- 所有角色从一开始就存在于世界观中
- Phase只是"在什么场景下引入最自然"

## 设计哲学

三层分离：
```
第1层：世界观框架（固定） — 天道种子/武道/炼狱/噩梦
第2层：角色人格（贴合原作） — 性格/对话/行为/NSFW
第3层：剧情走向（开放） — 不预设事件顺序，不锁定结局
```

核心区别：
- 线性方案：删掉所有轨道，让AI自由发挥
- 中间路线：保留轨道但不锁死，AI可以沿轨道走也可以脱轨

## Pitfall: 开放性改造后的验证清单

执行开放性改造后，必须逐项验证以下4点（不能只看文件大小和条目数）：

| # | 检查项 | 正确状态 | 常见遗漏 |
|---|--------|---------|---------|
| 1 | 事件条目enabled | False（故事种子库） | 改了内容但忘了改enabled |
| 2 | 开场白锁定词 | 无"第一次"/"初到"/"已堕落"等 | ALT1-5只改了部分，遗漏2-3个 |
| 3 | 预处理脚本触发逻辑 | 只有"阈值+提示"，无"自动触发" | P3-P6仍然有auto-trigger代码 |
| 4 | 角色条目措辞 | "特征库"/"可能表现出" | 只改了comment没改content |

**验证代码**：
```python
for e in entries:
    comment = e.get('comment', '')
    content = e.get('content', '')
    # 检查事件条目enabled
    if '事件' in comment and e.get('enabled', True):
        print(f"⚠️ id={e['id']} {comment}: 事件条目仍是enabled=True")
    # 检查预处理脚本
    if '预处理' in comment:
        if '自动触发' in content or '自动跃迁' in content:
            print(f"⚠️ id={e['id']}: 预处理仍有自动触发逻辑")

# 检查开场白锁定词
lock_words = ['第一次', '初到', '已堕落', '已经堕落']
for i, g in enumerate(alt_greetings):
    for w in lock_words:
        if w in g:
            print(f"⚠️ ALT{i+1}: 包含锁定词'{w}'")
```

## 大型结构化卡启发：开放性卡的补充设计模式（2026-07-11）

### 环境锚定与反动态等级

大型结构化卡的核心设计：NPC不是随机生成的，而是基于**地点评级**决定遭遇难度和NPC类型。世界不变，玩家自己选择去哪——这是"真实感"的来源。

**移植到开放性NSFW卡**：
- 给每个场景定义安全等级（S/A/B/C/D）
- 定义该场景的NPC分布概率和事件概率矩阵
- 时间和特殊条件影响概率
- 玩家通过选择场景来管理风险，而非依赖隐形难度曲线

详见：模板十九「场景环境锚定」

### 随机池在开放性卡中的应用

大型结构化卡用 `{{roll}}` 和性格池机制确保AI不偷懒重复——不是让AI"随机选"，而是**预生成随机结果让AI"依次取用"**。

**移植方案**（不需要MVU）：
- 使用ST内置的 `{{random::A,B,C,D,E}}` 在常驻条目中预生成随机事件/天气/NPC类型
- AI从预生成的列表中依次取用，而非自己"随机"选择
- 确保多样性——AI不会倾向于重复使用同一种选项

详见：模式六「随机池（轻量版）」在可移植设计模式手册中

### 事件种子的触发条件设计

大型结构化卡的DLC事件是**变量驱动**的——不是关键词触发，而是通过 `getvar` 检测当前状态决定是否触发。这确保了事件只在"故事准备好了"时才发生。

**纯文本降级方案**（enabled=false种子库模式）：
- 事件条目默认 `enabled=false`
- 在content中写明确触发参考（阈值+场景+时间+前置事件）
- AI根据当前叙事状态自行判断是否触发
- 分支设计不是"选A或B"，而是"不同行动→不同叙事走向"

详见：模板十五「事件分段标记」

## Manifest v2 映射：什么时候才叫 open_sandbox

本案例的“阶段=推荐引入场景、事件=可选触发”经验可以作为 `open_sandbox` 的设计来源，但不能只凭 `enabled=false` 或“事件种子库”自动判型。项目必须在 Manifest v2 中显式声明：

```json
{
  "narrative_mode": "open_sandbox",
  "routing_mode": "flat",
  "runtime_driver": "native_st",
  "sandbox_scope": "focused",
  "event_policy": "candidate_pool",
  "transition_policy": "none"
}
```

`open_sandbox` 的 sidecar 仍应使用 `narrative-contract.json` 描述候选事件的入口、NPC主动性、可中断性、多个可能结果和失效条件；每个候选事件还必须显式 `auto_fact: false`，不能因为被列入候选池就自动写成既成事实。它不要求 `transition_conditions`，也不应把事件编号写成必须按顺序完成的路线。Manifest 必须显式声明 `sandbox_scope`：`focused` 只要求一组可用的人物、场景和行为入口，`ensemble` 才要求当前的两组入口；未声明时保留旧版 2/2/2 规则。`audit_open_sandbox_entries.py` 还负责检查 NPC 主动行为以及“没有候选事件时世界仍可继续”的连续性证据；`audit_candidate_event_semantics.py` 负责检查事件合同，而不是扫描正文里有没有“可能”二字。

如果阶段仍承担明显的长线记忆边界和结果驱动转换，应选择 `soft_stage`，而不是把它误标为 open sandbox。反过来，严格的节点导航器（例如由外部脚本保存当前步骤的卡）应声明 `linear_stage` + `runtime_driver=external_extension`，不能拿本案例证明它是开放世界。
