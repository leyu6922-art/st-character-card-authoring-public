# NTL视角转换指南

当用户要求将苦主视角（{{user}}=受害者/旁观者）的角色卡转换为NTL视角（{{user}}=征服者/施害者）时，按以下流程操作。

## ⚠️ 第一原则：保留原文角色设定，只改视角和结构

**NTL转换 ≠ 重新设计角色。** 用户说「NTL版」时，期望的是：
- 原文所有角色的外貌/性格/对话/行为模板 **全部保留不变**
- 只改谁是 `{{user}}`、谁是NPC、叙事视角从谁出发
- 可以调整角色之间的关系结构（如「同一人多种形态」→「独立的人」）

❌ **绝对禁止**：发明原文中不存在的新角色来替换原有角色
❌ **绝对禁止**：改写原文角色的对话风格、行为模式、外貌特征

## ⚠️ 「原文形象」的歧义判断（2026-07-05 示例游戏项目v3案例）

当用户说「保留user作为原文形象」「user是原著中的角色」时，**必须确认{{user}}是指哪个角色**：

- **NTR/NTL题材中**：「原文形象」可以指：
  - 苦主（被绿的丈夫/男友）→ {{user}}=苦主视角，体验被NTR
  - NTR执行者（征服者/黑人/第三者）→ {{user}}=征服者视角，体验NTL
- **不要默认{{user}}=苦主！** NTR题材的玩家更可能想扮演征服者

**示例游戏项目v3实测案例**：
- 用户说「保留user作为小说中的原文形象」→ 代理默认{{user}}=指挥官（苦主）
- 用户纠正：「user作为原文黑人，NTL」→ {{user}}=马库斯（黑人佣兵，NTR执行者）
- 结果：整张卡需要重写（开场白、system_prompt、关系矩阵全部从苦主视角改为征服者视角）

**正确做法**：当NTR/NTL题材且用户未明确指定{{user}}身份时，**主动询问**：
```
{{user}}要扮演谁？
A. 苦主/被绿者（体验被NTR的痛苦）
B. 征服者/NTR执行者（体验NTL的快感）
```

## ⚠️ 旧卡迁移时的字段缺失问题（2026-07-05 示例游戏项目v3案例）

从旧卡迁移条目时（如`deepcopy(old_entries[idx])`），旧卡可能缺少TavernAI要求的字段：
- `case_sensitive`（布尔值，默认False）
- `name`（字符串，通常与comment相同）

**症状**：验证脚本报错 `条目[X] 缺少: ['case_sensitive', 'name']`

**修复**：迁移后统一补全：
```python
for e in entries:
    if "case_sensitive" not in e:
        e["case_sensitive"] = False
    if "name" not in e:
        e["name"] = e.get("comment", f"entry_{e.get('id', 0)}")
```

**正确做法**：迁移后立即跑验证脚本，不要等到最后才查。

## ⚠️ 单NTR角色卡的多P场景重写（2026-07-05 示例游戏项目v3案例）

当NTR角色从多个缩减为1个时，原有的「多NTR角色轮奸」场景无法实施。

**错误**：保留旧的多NTR场景描述（如"7个NTR角色轮番征服"）
**正确**：改为「{{user}}一人独战多舰娘」模式：
- 轮奸 → {{user}}轮流征服多个舰娘
- 双飞 → {{user}}+2个舰娘
- 群交 → {{user}}+所有舰娘

## 核心改动清单

### 1. system_prompt
- 改变{{user}}的角色定义：从"苦主/儿子"改为"征服者/大哥"
- 改变AI扮演的角色：原来AI扮演反派，现在AI扮演苦主+其他NPC
- 叙事框架：第一人称从苦主改为征服者
- 状态栏：增加征服者视角的状态字段

### 2. first_mes
- 完全重写为征服者视角的开场
- 保留原世界观和角色设定
- 从征服者的角度描写目标的外貌（更直接、更带有侵略性）
- 加入征服者的内心独白和目标

### 3. alternate_greetings
- 全部重写为征服者视角
- 保留原场景但改变叙述角度
- 加入苦主NPC的反应描写
- 如果原设定有多个征服者，展示「可拆开行动」的场景（如A去攻略X，B去攻略Y）

### 4. 世界书条目修改

**需要修改的条目：**
- 全局规则：改变{{user}}角色定义，标记NPC角色
- 叙事控制：改变人称和视角限制
- 苦主角色：从玩家角色改为NPC，加入"AI必须按阶段描写"的指令
- 关系矩阵：调整为NTL关系结构
- 状态栏：增加{{user}}（征服者）的状态字段

**不需要修改的条目：**
- 地点条目（视角无关）
- 目标角色核心设定（角色本身不变——外貌/性格/对话/行为全部保留）
- 系统条目（性爱规则、状态栏格式等——除视角相关部分外）
- 剧情节点（可保留原节点，按需调整描述角度）
- 对话示例库（保留原文对话，这是原著素材）
- 文风示例库（保留原文文风）

### 5. 角色条目调整（最小改动）

**征服者角色（变成{{user}}）：**
- keys: 加入「大哥」「领头」等关键词
- comment: 标注「{{user}}」
- content: 保留原文设定，在开头加「{{user}}扮演」标记
- 如果有「同一人多种形态」设定：改为「独立的人，X为大哥，Y/Z为小弟」

**小弟角色（保持独立）：**
- keys: 不变或加入「小弟」
- content: 保留原文设定，加入「听大哥指挥但可拆开单独行动」
- 如果原文是「同一人多种形态」：去掉「可合体可分身」，改为「三个独立的人」

**苦主角色（变成NPC）：**
- keys: 去掉「user」
- content: 保留原文设定，将「{{user}}扮演」改为「{{char}}扮演（NPC）」

## 备份规范

转换前必须：
1. 备份原版：`xxx_苦主版备份.json`
2. 新建NTL版：`xxx_NTL版.json`
3. 两个版本都保存到同一目录

## 「可拆开行动」机制

当原设定有多个征服者时（如三人组），NTL版应强调：
- 大哥（{{user}}）可以指挥小弟们行动
- 小弟们可以拆开单独行动，分别攻略不同目标
- 也可以合体一起行动
- 在开场白中展示「远程指挥」「分配目标」等场景

## JSON构建方法（关键pitfall）

### ❌ 错误：一次性构建完整JSON

用Python脚本一次性copy.deepcopy + 赋值所有字段 + json.dump，中文字符串拼接导致first_mes和alternate_greetings被截断到原长度的40-60%。

**根因**：Python多行字符串拼接在长中文文本中容易出现隐式截断，尤其是通过write_file写入再terminal执行的流程中。

### ✅ 正确：load-and-patch两步法

**步骤1**：copy.deepcopy原卡 → 修改顶层字段（name/description/personality/scenario/system_prompt）→ 逐条patch世界书条目 → 保存中间结果

**步骤2**：单独写patch脚本，json.load中间文件 → 修改first_mes和alternate_greetings → json.dump保存

**关键**：first_mes和alternate_greetings（长中文文本）必须在独立脚本中处理，不要和其他字段混在一个脚本里。

## 后转换验证（必须执行）

NTL转换完成后必须验证：
1. first_mes ≥ 1400字
2. 每个alternate_greeting ≥ 1400字
3. spec = chara_card_v3
4. v3顶层15字段完整
5. 世界书条目格式（extensions/addMemo）

如果greeting字数不足，写第二个patch脚本在现有文本末尾追加内容（不要重写整个greeting）。

## 踩坑案例

### ❌ 错误案例：示例角色项目NTL转换（2026-07-04）

**原设定**：反派三人组 = 富公子（计谋）+ 肥猪男（暴力）+ 小鬼（身份便利），同一人三种形态

**错误做法**：发明了三个全新角色（陆少卿/阿铁/小宝），完全替换原著角色
→ 用户纠正：「不对，三人组依旧是那三个NTR角色，不要改原文设定」

**正确做法**：
- 富公子 = {{user}}大哥（保留原设定）
- 肥猪男 = 小弟A（保留原设定，听大哥指挥）
- 小鬼 = 小弟B（保留原设定，听大哥但常自作主张）
- 去掉「同一人三种形态」→ 改为「三个独立的人」
- 所有对话/行为/外貌描写保留原文不变

**教训**：NTL转换的第一步是读取原文所有角色设定，理解后再动手。不要跳过读取直接设计新角色。
