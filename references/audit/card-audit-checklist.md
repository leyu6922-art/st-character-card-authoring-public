# 角色卡审查工作流（Card Audit）

当用户说"审查这个卡""看看有没有问题""对比规划书检查"时，使用此流程。与"从零构建"和"修卡"不同，审查是**诊断式分析**——找出卡与规划书/原文之间的不一致。

## 审查流程（4步）

1. **读取卡JSON** — 用 `execute_code` + `json.load()` 解析，输出条目数/大小/结构概览
2. **读取规划书/质检文档** — 用 `read_file` 读取所有关联的 .md 文件
3. **逐维度交叉验证** — 按下方检查清单逐项比对
4. **输出审查报告** — 按 🔴关键/🟡重要/🟢优化 三级分类

## 审查检查清单（14项）

| # | 检查项 | 级别 | 检查方法 |

## Pitfall

### 不要报错uid字段

ST v3 spec中uid是optional字段，id才是标准字段。条目没有uid不会导致兼容问题。审查时不要把"无uid"列为问题。

### constant=True的条目容易漏数

用代码统计，不要肉眼扫。实测：首轮报告说"只有2条constant"，实际有10条。

```python
constant_entries = [i for i,e in enumerate(entries) if e.get('constant') == True]
print(f"constant=True: {len(constant_entries)}条")
```

### 变量名"不一致"可能是假阳性

预处理脚本用 `getMessageVar('stat_data.王启.妖神觉醒度')` 读取变量，
其他条目content中写"妖神觉醒>=70"——这只是自然语言描述，不是变量路径。
只要脚本读写的路径和规则中定义的路径一致就行，content中的简称不影响运行。

**判断方法**：检查entry[86]变量更新规则中的变量名是否与entry[85]预处理脚本的路径一致。如果一致，其他条目中的简称只是"人类可读描述"，不是bug。

## Key冲突治理策略（2026-07-07 示例玄幻项目案例）

当多个条目共享同一关键词时，ST会同时触发所有匹配条目，导致冗余 token 注入和潜在的指令矛盾。

**分级治理原则**：
- **3+条共享**：必须修复，这是真正的 token 浪费
- **2条共享**：优先级低，收益小，改了反而可能误伤，可暂不处理

**修复策略**：
1. **constant 条目优先保留 key**（因为 constant 每轮都注入，key 影响不大）
2. **非 constant 条目改更精确的 key**（如"收徒"→"拜师"，"迷奸"→"迷奸场景"）
3. **不要删除 key**（宁可改精确也不要删，否则条目永远不会被触发）
4. **constant 条目的冗余 keys 应清空**（constant=true 时 keys 不起作用，留着增加无用数据）

**实测效果（示例玄幻项目）**：3+条共享从10个降至0个，总冲突从36个降至26个，34处 key 修改涉及20个条目。

## 死变量检测（2026-07-07 示例玄幻项目案例）

变量更新规则（entry 134）定义了变量，但预处理脚本不读不写它，也没有任何条目说明它如何变化。这是"死变量"——定义了但永远不会被使用。

**检测方法**：
1. 从变量更新规则中提取所有变量路径
2. 在预处理脚本中搜索 `getMessageVar` 和 `setMessageVar`，列出所有读写的变量
3. 对比两列表，规则中定义但脚本中未出现的 = 死变量

**修复方案**（3选1）：
- **方案A**：从规则中删除死变量（最简单）
- **方案B**：在预处理脚本中补读取+提示（推荐，v2精神：提示不强制）
- **方案C**：启用相关事件条目（最完整但增加 token）

**实测案例（示例玄幻项目）**：`龙傲天.前世记忆` 变量在规则中定义了 `无/片段觉醒/完全觉醒` 三个状态，但脚本不读不写。修复：在脚本中补读取 + 太一觉醒>=60时输出提示。

## 交叉验证方法（多窗口审查时）

当用户在另一个窗口也做了审查并提供结果时：
1. 逐项验证对方的结论（用代码确认，不靠记忆）
2. 标注每项为 ✓确认/❌误报/⚠️需确认
3. 对方报错的条目ID要重新核实（实测：对方报的ID可能不对）
4. 补充对方遗漏的问题（如预处理脚本死代码、规则-脚本矛盾）

详见 `references/audit/card-cross-verification-workflow.md`。
