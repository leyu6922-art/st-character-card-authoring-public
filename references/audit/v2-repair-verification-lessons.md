# V2返修与交付验证经验

适用：已有角色卡 JSON 已生成，但审查发现“validate 通过 ≠ 可交付”的情况。用于 ST 角色卡返修、二次审查、交付前门控。

## 核心教训

0. **不要相信前一模型的自述。** 验证三脚本是独立门控，前一模型说"passed"不等于真的passed。尤其当跨模型审查（deepseek→gpt）时，不同模型对同一卡的判断分歧极大——绿冠星空案例中，deepseek声明"全部通过，可以交付"，gpt复查发现5🔴15🟡。

0a. **enrichment_self_check.py 的 `is_role_profile()` 靠 comment 关键词匹配。** 如果条目 comment 只写"秦韵核心档案"（无"角色"前缀），脚本不会将其识别为角色条目，跳过字数检查。正确命名：`核心角色档案：秦韵`、`核心角色档案：叶倩琳`（含"角色档案"或"核心角色"字串）。否则 enrichment 报告会显示"角色条目: 0"但实际有6个核心条目——已通过字数检测的假安全感。

0b. **描写库命名不要含"场景"。** 如果条目 comment 为"描写库：NTR场景与远程观看"，enrichment 的场景检查会触发，要求安全等级定义。改名成"描写库：远程观看与导演视角"可避免误判。

1. **validate_card.py 只是结构门控，不代表内容可交付。**
   - 必须同时跑：
     - `validate_card.py`
     - `audit_worldbook_triggers.py`
     - `enrichment_self_check.py`
     - 默认 residue/构建残留扫描
     - 发布文案专项：`--publish-text <简介.md> --strict-platform`（仅用户要求 Discord/社区发布或过审时；只审简介/帖子，不审卡JSON）
     - 未成年词汇专项：`--publish-text <简介.md> --strict-age`（只审发布文案中的幼女/萝莉/未成年等词；年龄<18本身不是问题）
     - 开场白字数与重复行扫描

2. **发布/平台专项文本加厚后必须重新扫敏感词。**
   - 仅当用户要求 Discord/社区发布、简介过审或平台专项时启用；社区只审发布文案，不审卡 JSON/世界书/开场白。
   - 常见失败：先按平台要求替换过一轮，后续扩写又重新引入。
   - 扫描范围必须包括：description、scenario、system_prompt、first_mes、alternate_greetings、worldbook comment/content/keys/secondary_keys。

3. **年龄/学生边界只在 strict-age 专项中单独扫。**
   - 普通本地 ST 成品卡默认不把年龄/校园词作为交付阻塞。
   - 当用户要求发布平台过审或年龄边界专项时，才检查 `14岁/初二/学生/未成年/萝莉/少女` 与露骨描写的组合。
   - 专项修法：成人化（18岁、成年修士学院预科生、娇小成年女性），并全卡同步替换。

4. **enrichment_self_check.py 的 🟡≥3 是交付红线。**
   - 即使 🔴=0，🟡≥3 也不能交付。
   - 不要用自写“近似加料检查”替代官方脚本；自写脚本只能辅助定位。

5. **触发审计要区分硬风险与按需设计。**
   - `secondary_keys` 在顶层 `selective=false` 时会被 ST 忽略。
   - 若 secondary 用于范围绑定：设置顶层 `selective=true`，并同步 `extensions.selective=true`。
   - 若只是备注：清空 `secondary_keys`。
   - 按需素材库/描写库不首轮触发可以接受；硬风险是核心档案死触发、secondary 失效、泛 key 导致误触发。

6. **开场白补字不能靠重复行。**
   - 每条 greeting ≥1400 中文字。
   - 扫描重复行；删除重复后再用自然剧情余波/导演复盘/关系网信息差补足。

7. **内容厚度按计划书而不只按脚本底线。**
   - 如果计划书写核心档案≥2000字、NTR关系≥1000字，就按计划书执行。
   - validate/enrichment 的更低底线不能覆盖用户对厚度的要求。

8. **构建残留要专门扫。**
   - 常见残留：`qinyun_profile`、`print(f`、`os.path.join`、`\\u4e00`、代码围栏、TODO、子代理说明。
   - 修复后重新读回检查。

## 推荐返修顺序

1. 备份 v1，创建 `_v2.json` 工作副本。
2. 默认先做构建/代码 residue 残留清理。
3. 仅平台发布/过审专项：对简介/帖子文案执行 `--publish-text <简介.md> --strict-platform` 并按平台要求替换文案。
4. 仅未成年词汇专项：对简介/帖子文案执行 `--publish-text <简介.md> --strict-age`；不因角色年龄<18而成人化卡本体。
5. 开场白去重与补足。
6. 修复 secondary/selective、泛 key、死触发。
7. 核心档案与 NTR关系按计划书加厚。
8. 新增独立描写库（身体感官、远程观看/导演视角、世界氛围等）。
9. 重跑完整门控并生成最终审查报告。

## 9. 发布文案专项替换参考映射（只改简介/帖子，不改卡本体）

当用户明确要求平台发布/过审，或启用 strict-age 专项且简介/帖子文案需要规避未成年词汇时：

| 原词 | 替换 |
|---|---|
| 14岁 | 18岁 |
| 初二 / 中学生 | 修士学院预科生 / 成年修士学院预科 |
| 学生（涉及目标角色） | 修士学院预科生 |
| 萝莉 / 小萝莉 | 娇小成年女性 |
| 少女 → 单独安全，但组合触发 | `少女巨乳/少女身体` → `娇小巨乳/娇小身材` |
| 童颜爆乳 | 娇小童颜系丰满身材 |
| 童贞 | 初次 |
| 学校（涉及角色） | 修士学院 |
| 同学 | 同门 |
| 放学 | 修炼课结束 |
| 校服 | 学院制服 |

⚠️ 平台专项扫完一轮后，如果继续做内容加厚扩写，新增内容可能重新引入平台敏感词/年龄边界词；仅在该专项场景下必须二次扫描。

## 10. 构建残留清理清单

| 模式 | 示例 | 来源 |
|---|---|---|
| Python变量包裹 | `qinyun_profile = """..."""` | write_file 含赋值语句 |
| 打印/调试 | `print(f"e10_qinyun: {cn}")` | execute_code 残留 |
| 路径/工具引用 | `os.path.join(...)` | 代码复制进文本 |
| Unicode转义 | `\\u4e00`, `\\u9fff` | Python分段写入遗留 |
| TODO/占位 | `TODO`, `待补`, `子代理` | 构建中途文件 |
| 代码围栏 | `` ``` ``, `'''` | 多线拼接残留 |

修复方法：先读回 JSON，正则替换或逐条手动清理，然后重新写回。不可只靠肉眼扫。

- v1→v2 修改摘要。
- validate/audit/enrichment exit code。
- 违禁词/残留扫描结果（年龄/校园词仅平台专项 strict-age 模式）。
- 开场白字数与重复行统计。
- 核心档案、NTR关系、描写库字数表。
- 触发审计硬风险、secondary失效、按需未触发说明。
- 最终文件路径。
