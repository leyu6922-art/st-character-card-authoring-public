# 跨窗口 Skill 治理与复核模式

> 适用场景：多个 Hermes 窗口/代理同时审查或修复同一个 skill；一个窗口给出审查报告，另一个窗口指出部分问题已被修复或发现二阶问题。

## 核心原则

**审查报告是线索，不是当前事实。** 当另一个窗口反馈“报告已过时/部分已修复”时，必须回到当前真实文件和最小 fixture 重新核验，不要按旧 P0 清单机械执行。

## 标准流程

1. **读取当前真实文件状态**
   - 核对 `SKILL.md`、相关 `scripts/`、`references/audit/` 的当前内容。
   - 明确报告版本与当前版本是否一致。

2. **逐项验证旧报告的 P0/P1**
   - 对每个“已修/未修”的争议项做实际检查。
   - 自动化问题必须用最小 fixture 验证，不只看文本。

3. **识别二阶断点**
   - 修复一个 validate 检查后，检查相邻检查是否会误杀同一合法结构。
   - 示例：G 型选开模式修了 `all_greetings` 后，还要验证 `enabled=false` 检查是否误杀 `constant=true + enabled=false` 的身份条目。

4. **重新排序执行清单**
   - 已修的旧 P0 降级为“历史发现/回归测试”。
   - 当前真实阻断点优先。
   - 如果 validate P0 已闭合，转入结构一致性治理（决策树、模板映射、审查体系、索引）。

5. **做最小补丁 + 回归验证**
   - 对脚本修复：`py_compile` + 最小合法 fixture + 最小非法 fixture。
   - 对文档修复：检查重复标题、死链、锚点、字面 `\n` 表格残留、关键术语是否一致。

6. **沉淀修复记录**
   - 把跨窗口发现和二阶断点写入 `references/audit/full-process-skill-audit-findings.md` 或本文件。
   - 不把“某窗口说了什么”当长期规则；沉淀的是复核方法和回归测试模式。

## 最小 fixture 模式

验证脚本类修复时，至少准备两类 fixture：

- **合法最小卡**：覆盖新允许结构，例如 G 型选开身份条目：
  - `constant=true`
  - `enabled=false`
  - `keys` 非空
  - `comment` 含「选开」或「身份」
  - `content` 含 `{{user}}`
- **非法最小卡**：故意缺字段或违反规则，例如 `extensions` 缺 31 字段白名单中的一批字段。

期望结果：合法 fixture `passed=True`，非法 fixture `passed=False` 且错误信息指向目标规则。

## 常见误区

| 误区 | 正确做法 |
|---|---|
| 看到旧报告 P0 就直接修 | 先验证当前文件；可能已经被另一个窗口修掉 |
| 修了一个脚本报错就宣布完成 | 跑相邻检查的合法/非法 fixture，防二阶误杀 |
| 手工一条条修腐烂索引 | 用脚本按真实目录重建 active / archived / deleted |
| 把交叉验证结果写成任务叙事 | 写成可复用流程、fixture、回归检查 |
| 两个窗口结论冲突时凭直觉选一个 | 当前文件 + 可执行验证结果优先 |

## 适用于本 skill 的治理顺序

当 validate 主断点已经闭合后，优先顺序通常是：

1. 合并重复流程段落（如重复 §2.5）
2. 修决策树覆盖和原型命名冲突
3. 补默认模式的硬性检查清单（如 G 型选开模式）
4. 补审查体系显式行（如 F 型）
5. 最后脚本重建 §7 索引

不要把系统性腐烂索引当作一条条死链手修；最后统一生成。
