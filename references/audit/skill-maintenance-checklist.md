## 一、文件完整性检查

### 1.1 重复文件检测

references/ 目录做过"平铺→子目录"重组后，根目录旧副本可能残留。

```python
import os
base = "references"
root_files = {f for f in os.listdir(base) if os.path.isfile(os.path.join(base, f)) and f.endswith('.md')}
subdir_files = set()
for d in os.listdir(base):
    dp = os.path.join(base, d)
    if os.path.isdir(dp):
        for f in os.listdir(dp):
            if f.endswith('.md'):
                subdir_files.add(f)
duplicates = root_files & subdir_files
print(f"重复: {len(duplicates)} 个")  # 应为0
```

**健康指标**：重复文件 = 0。

## 二、内容一致性检查

### 2.1 数字一致性

模板数量、检查项数量等硬数字在多处引用时必须一致。

**已知坑**：
- 模板库从12个扩展到19个后，`template-evaluation-workflow.md` 和 `sillytavern-scripting-patterns.md` 仍写"12个模板"

**检查方法**：搜索所有文件中的 `(\d+)个模板` 和 `(\d+)项检查`，确认数字与实际一致。

### 2.2 版本一致性

SKILL.md 头部版本号、模板库版本号、validate_card.py 版本注释应一致。

### 2.3 路径一致性

SKILL.md §7 索引中的路径必须与实际目录结构匹配。重组目录后索引必须同步更新。

## 三、流程完整性检查

### 3.1 §2→§3 桥接

从"分析阶段"到"构建阶段"之间必须有**模板匹配步骤**。没有这一步 = agent 不知道在构建时用哪个模板。

**修复**：§2.3 计划书策略之后增加 §2.5 模板匹配，列出"这个卡需要哪些模板"的决策流程。

### 3.2 系统条目常驻/触发分类

§3.5 系统条目清单不能只列"必须包含"，必须区分哪些 constant=True、哪些 constant=False。不区分 = 创作者全设成常驻 → token 爆炸。

### 3.3 validate_card.py 豁免逻辑

豁免条件不能依赖 `constant=True + comment 关键词`（常驻→触发后豁免失效）。应使用**内容特征**（content 中的关键词）作为豁免依据。

**已修复案例**：
- check 18 `<maintext>` 检测：用 `输出格式/TXT格式/正文格式` 在 content 中判断是否格式指令
- check 23 状态栏字符：用 `状态栏/格式增强/输出格式` 在 comment 或 content 中判断

## 七、流程可执行性审查（2026-07-13 新增·双窗口审计方法论）

**§1-§6 是静态文件检查。本节是动态流程审查——模拟 agent 视角，走通整个制卡链路，发现断点。**

### 7.1 审查维度（A-H）

| 维度 | 核心问题 | 检查方法 |
|------|---------|---------|
| A. 入口与决策流 | 决策树是否覆盖全部原型？agent 能否自主走到正确分支？ | 逐个原型对照决策树 → 确保每条路径可达 |
| B. 分析阶段 | 分析步骤是否可执行？前置门控是否有效？ | 模拟 agent 从 §2.1→§2.7 逐步执行 |
| C. 构建阶段（G型） | 两种模式（选开/greeting）是否各有完整构建指导？ | 对比两种模式的流程步骤 → 检查清单对称性 |
| D. 构建阶段（通用） | 门控表是否覆盖全部原型？加料自检脚本是否可执行？ | 逐原型对照门控表映射 |
| E. 审查与验证 | validate_card 检查是否有重叠/遗漏/矛盾？审查模板是否全覆盖？ | 审计 validate_card.py 代码 + 审查模板对照 |
| F. 发布与维护 | Discord 格式规则是否清晰？pitfalls 是否同步？ | 检查 §5.3 格式选用规则 + pitfall-library 与 §5.1 一致性 |
| G. 跨章节一致性 | 内部锚点/版本号/模板数量/旧版引用是否一致？ | 自动化脚本搜全文件 |
| H. 边界与缺失 | 异常路径（预处理失败/NSFW过滤/4+身份）是否有回退？ | 穷举异常场景 → 检查 skill 覆盖 |

### 7.2 审查方法论

**双窗口交叉审查模式**（2026-07-13 验证有效）：

```
窗口A（本窗口）：审查代码/JSON/结构/脚本 → 发现断点 + 精确行号
窗口B（另一窗口）：审查内容/剧情/规划书对照 → 发现语义矛盾
→ 合并发现 → 排重 → 分级（🔴断点/🟡模糊/✅通过）
```

**实战数据**（本次 session）：
- 发现 6 个 🔴 断点 + 9 个 🟡 模糊点
- 窗口B 验证后：认可 6🔴 + 7🟡，降级 1 个（H5），升级 1 个（E1→🔴）
- 交叉验证使误报率从单窗口 ~12.5% → 0%

### 7.3 新增设计模式后的上下游衔接验证（§8 补充）

这是 §8 已有规则的**自动化检查清单**版本：

```
新增一个设计模式/原型变体 → 逐点检查：
  □ §1.0 决策树：有分支能走到新模式？
  □ §1.1 原型表：有该行？
  □ §2.5 模板匹配：列出该模式需要的模板/参考文件？
  □ §3 构建阶段：有构建子节或跳转指令？
  □ §3.4 交付门控表：有该模式 → 审查模板的映射？
  □ §4.0 审查表：有该行（带审查维度）？
  □ §7 参考文件索引：新参考文件已添加？
  □ §0 快速索引：重要模式有跳转行？
```

**反面案例**（G型 v6.16→v6.17）：新增了完整设计文档（2个参考文件 + §1.4），但7个衔接点全部断裂——agent 无法自然走到 G 型，必须"提前知道它存在"。

**本次 session 新增案例**（F型）：F型在 §1.1/§1.3 有完整定义，但决策树完全没给它入口路径——"加 G 型时忘了同步 F 型"。

### 7.4 常见审查发现模式

| 发现模式 | 根因 | 检测方法 |
|---------|------|---------|
| 原型在§1.1有定义但决策树无路径 | 新增原型时只更新了表，忘了改决策树 | 逐原型对照决策树 |
| 门控/审查表缺变体行 | 新增子变体（A-N/A-N×E）时只更新了§1.0，忘了§3.4/§4.0 | 搜索子变体名 → 确认在门控表+审查表中出现 |
| 代码块重复 | 编辑时 copy-paste 残留 | 搜索相邻相同注释头 |
| 双文件不同步 | 一个真相源分裂为两个文件（如 pitfall-library vs SKILL.md §5.1 各自维护陷阱列表） | 对比两个文件的条目数量差异 | **修复模式**：不要机械同步（33条复制粘贴=未来双倍维护负担）。改为**定位重定义**：一个文件=权威完整列表（SKILL.md §5.1），另一个=详细补充版（pitfall-library.md）。然后在所有引用处更新为双文件引用（如 §3.4 第⑧步从单文件改为 `先读 §5.1 → 再查 pitfall-library.md`） |
| 版本号残留 | 更新了版本行但正文参考未同步 | 搜索旧版本号（如"6模板""35项检查"） |
