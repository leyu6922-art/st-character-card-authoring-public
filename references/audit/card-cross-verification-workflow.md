# 角色卡交叉验证工作流（Card Cross-Verification Workflow）

## 适用场景

- 用户在多个窗口同时审查同一张卡
- 需要对比不同审查报告的结论
- 用户提供另一窗口的审查结果要求验证
- **用户有系统性的双窗口审查习惯**（2026-07-03~09 实测6个案例）

## 双窗口审查模式概览

用户在7天内至少在以下场景使用了双窗口互审：

| # | 日期 | 场景 | 窗口1 | 窗口2 | 核心发现 |
|---|------|------|-------|-------|---------|
| 1 | 7/4-5 | 叶无云截断排查 | Hermes：排除8个原因，修v2→v3 | Codex：发现递归触发链 | 窗口1漏掉了真正根因 |
| 2 | 7/5 | 批量旧卡验证 | 跑validate_card 22张卡 | 验证"流程可复现" | 确认修复不是临时补丁 |
| 3 | 7/5 | 周雨晴卡审查 | validate_card 89个错误 | Codex独立结构审查 | 发现数据不一致(14条vs82条) |
| 4 | 7/7 | 示例玄幻项目代码审查 | 代码级21项问题 | 内容级3个误报 | 去掉3个误报(12.5%→0%) |
| 5 | 7/9 | 模板库兼容性 | 评估P0-P3分类 | 二次审查补4个遗漏 | 框架+补充→v2.0修订 |
| 6 | 7/9 | source code验证 | 声称placement值 | 查ST源码确认 | 源码为终极仲裁 |

## 何时启动双窗口（决策树）

```
任务复杂度评估：
├─ 做新卡（条目<30）→ 单窗口够用
├─ 做新卡（条目>30，新类型机制）→ 框架阶段单窗口，完成后可考虑互审
├─ 修旧卡 → 强烈建议双窗口（旧卡坑多，单窗口漏概率高）
├─ 批量验证/修复 → 双窗口（一个跑脚本，一个验证"可复现"）
├─ 预设兼容性审查 → 双窗口（一个评估分类，一个查遗漏的regex冲突）
└─ 截断/空回排查 → 双窗口（一个排查常见原因，一个查深层根因如递归链）
```

## 适用场景表

| 场景 | 窗口1分工 | 窗口2分工 | 效果 |
|------|----------|----------|------|

| 复杂卡代码审查 | 代码/结构检查（字段/格式/脚本） | 内容/设计检查（设定/世界观/预设兼容） | 去误报+补遗漏，误报率从12.5%→0% |
| 预设兼容性审查 | 模板库兼容性评估（分类P0-P3） | 对评估做二次审查（补充遗漏的regex冲突） | 框架+补充合并到v2.0修订 |
| 截断问题排查 | 排除8个可能原因 | 独立验证+发现递归触发链 | 找到真正根因（单窗口漏掉了递归链） |
| source code验证 | 声称regex placement值 | 查ST源码确认 | 源码为终极仲裁 |
| NTL版审核 | 批量模式匹配扫描 | 处理JSON转义形式+误报过滤 | 三轮审查法覆盖转义陷阱 |

## 窗口分工原则

| 窗口 | 专长 | 擅长发现 | 容易遗漏 |
|------|------|---------|---------|
| 代码/结构窗口 | JSON格式、字段完整性、脚本逻辑 | 格式错误、死代码、字段缺失 | 内容一致性、预设冲突 |
| 内容/设计窗口 | 设定合理性、世界观一致性、预设兼容 | 误报过滤、语义问题、regex冲突 | 脚本逻辑、递归触发链 |

**最佳组合**：代码窗口做"发现问题"，内容窗口做"过滤误报+补遗漏"。

## 核心价值量化

| 指标 | 单窗口 | 双窗口 | 提升 |
|------|--------|--------|------|
| 误报率 | 12.5% (3/24) | 0-1% | -92% |
| 问题发现数 | 中等 | +30-50% | 更全面 |
| 覆盖维度 | 偏代码或偏内容 | 代码+内容+源码 | 无死角 |
| 根因定位 | 表面问题 | 深层根因（如递归链） | 质的提升 |

### 修卡比做卡更需要互审

做新卡时单窗口通常够用（自上而下设计）。修旧卡时必须互审——旧卡坑多、格式混杂、历史包袱重，单窗口容易只修表面而漏深层根因（如递归触发链）。

## 典型案例详解

### 案例1：递归触发链是最常见的遗漏（7/4-5）

单窗口排查了8个可能原因，排除了7个，结论是"v2格式不兼容"。
双窗口的Codex独立验证发现：`prevent_recursion=False`导致43条链式触发（膨胀3.6倍），这才是截断的真正根因。

**教训**：单窗口容易只看格式不看递归，但递归触发链才是token爆炸和截断的真正根因。

### 案例3：数据不一致是高频误报来源（7/5）

窗口1说"14条世界书"，窗口2说"82条"。实际原因是窗口1看了旧缓存/旧优化版文件。

**教训**：双窗口互审能发现"看了旧缓存"这种单窗口难以自查的问题。

### 案例4：去误报避免无效修改（7/7）

窗口1报21项问题，窗口2发现其中3个是误报：
- "uid缺失"→ 实际是格式问题不是缺失
- "年龄矛盾"→ 不同阶段的外表年龄设定
- "常驻条目数量"→ 统计口径不一致

**教训**：不做互审就会基于误报做无效修改，浪费时间且可能引入新bug。

### 案例5：源码验证是终极仲裁（7/9）

两个窗口对regex placement值结论矛盾。用grep查SillyTavern源码：`WORLD_INFO: 5`。

**教训**：当两个窗口结论矛盾时，查源码/数据是最可靠的解决方式，不靠"谁说的更有道理"。

## 工作流

### 第一步：建立条目索引映射

对方报告可能用 `entry[X]`（数组索引）或 `ID=X`（条目id），两者不一定相同。

```python
for i, e in enumerate(entries):
    if i <= 10 or i >= len(entries) - 3:
        print(f"  entry[{i}] = ID={e['id']:3d} | {e.get('comment','')[:35]}")
    elif i == 11:
        print(f"  ... (省略) ...")
```

### 第二步：逐项验证

对对方报告的每一项：
1. 用代码确认数据（不靠记忆）
2. 标注为 ✓确认/❌误报/⚠️需确认
3. 特别注意：对方报的条目ID可能不对（用的是索引而非id）

### 第三步：补充遗漏

对方可能遗漏的问题类型：
- 预处理脚本死代码（typeof检查）
- 规则-脚本矛盾（规则定义了变量但脚本没实现）
- 死变量（定义了但无读写入口）
- 变量命名不一致（脚本路径 vs 规则定义）

### 第四步：综合报告

按优先级分类：
- 🔴 必须修（影响运行/安全）
- 🟡 应该修（影响一致性/质量）
- 🟢 可选优化

## Pitfall

### 交叉验证Pitfall：条目编号混淆（2026-07-07 示例玄幻项目案例）

对方报告中可能用 `entry[X]`（数组索引）而非 `ID=X`（条目id字段）。数组索引和条目id不一定相同（因为有ID空洞）。必须建立映射表再验证：

```python
# 建立索引→ID映射
for i, e in enumerate(entries):
    print(f"  entry[{i}] = ID={e['id']} | {e.get('comment','')[:30]}")
```

### 交叉验证Pitfall：验证代码变量引用bug

验证循环中 `e` 变量可能引用上一轮循环的值，导致输出错误数据：

```python
# ❌ 错误：e 引用上一轮循环的最后一个值
for eid in [133, 134, 135]:
    e = entry_dict[eid]
    print(f"ID={eid}: const={e.get('constant')}")
for eid in [3, 4, 88]:
    print(f"ID={eid}: keys={e.get('keys')}")  # ← e 还是135！输出的是135的keys

# ✅ 正确：每轮重新赋值 e
for eid in [3, 4, 88]:
    e = entry_dict[eid]  # ← 重新赋值
    print(f"ID={eid}: keys={e.get('keys')}")
```

## 常见误报

| 对方报的问题 | 实际情况 | 判断 |
|-------------|---------|------|
| 无uid字段 | ST v3中uid是optional，id是标准字段 | ❌ 误报 |
| 年龄矛盾（"三十年来"+"年近五十"） | 50-30=20岁开始守楼，数学自洽 | ❌ 误报 |
| 常驻条目只有2条 | 实际有10条（用代码统计，不靠肉眼） | ❌ 误报 |
| 变量名"妖神觉醒"vs"妖神觉醒度" | 后者是脚本变量路径，前者是自然语言描述，不影响运行 | ⚠️ 需验证 |

## 提案→执行差距分析（Skill 更新审查专用）

当审查另一窗口/会话的 **skill 更新工作**（如模板库扩展、参考文件新增）时，不能只验证"文件是否存在"。必须做提案与执行的差距对比。

### 适用场景

- 另一窗口分析了一张参考卡，产出了"分析报告 + 设计手册 + 更新提案"
- 另一窗口声称"模板库已从 vX 升级到 vY"
- 另一窗口的提案列出了"Phase 1-3 计划 + N 个新参考文件"

### 差距分析表格模板

```markdown
| 提案要求 | 实际执行 | 匹配？ |
|----------|---------|--------|
| 模板编号 21-25（5个） | 模板编号 13-18（6个） | ❌ 编号不一致 |
| 21. 分层逻辑防火墙 | 17. 反AI顺从机制 | 🟡 概念相近但命名不同 |
| 22. 道具品质与进化系统 | ❌ 未实现 | ❌ |
| 23. 六维性格编码 | 13. 人物描写结构化 | 🟡 关联但不完全等价 |
| ❌ 提案未提 | 14. 叙事节奏循环控制 | 🆕 执行新增（比提案好！） |
```

### 必须检查的5个维度

| # | 检查项 | 方法 | 常见问题 |
|---|--------|------|---------|
| 1 | **模板编号一致性** | 提案编号 vs 实际编号 | 提案用 21-25，实际用 13-18（提案用了旧编号范围） |
| 2 | **模板数量匹配** | 提案 N 个 vs 实际 N 个 | 执行时新增了提案没提的模板（方向偏离但可能更好） |
| 3 | **提案漏项** | 逐条勾选提案清单 | 明确列出的有价值模板被遗漏且无理由 |
| 4 | **参考文件空壳** | `read_file` + `wc -c` 检查文件大小 | 提案列出 N 个新文件，实际 0 个有内容（只有标题） |
| 5 | **Phase 完成度** | 对照提案的 Phase 1/2/3 逐项勾选 | Phase 1 只完成模板库部分，其余全空 |

### 关键判断：执行偏离是否合理？

执行偏离提案不一定是坏事——有时执行时发现了更好的方向：

- ✅ **合理偏离**：执行时新增了提案没提但更基础/更通用的模式（如"叙事节奏循环控制"比"道具品质进化"更通用）
- ❌ **不合理偏离**：提案明确列出的有价值项目被遗漏且无解释（如道具品质进化系统被标为"不需要"但模板八已有基础框架，只需补充示例）
- 🟡 **灰色地带**：实际执行的质量高于提案（新模板更好），但提案的某些有价值项被遗漏——需要补齐

**判断标准**：新方向更好 → 更新提案匹配执行。旧方向仍有价值 → 补上遗漏项。**两者都做**（更新提案 + 补遗漏）。

### 案例：大型结构化卡分析审查（2026-07-11）

另一窗口分析了大型结构化卡 v4.2（469条目/TRPG引擎），产出 3 份文档并更新了模板库。

**差距分析发现**：

| 提案（Skill更新提案 v1.0） | 实际执行 | 判定 |
|--------------------------|---------|------|
| 模板 21-25（5个） | 模板 13-18（6个） | ❌ 编号不一致 |
| 22. 道具品质与进化系统 | 未实现 | ❌ 遗漏（但模板八已有基础） |
| 24. 场景环境锚定 | 未实现 | ❌ 遗漏 |
| 6 个新参考文件 | 0 个有实际内容 | ❌ 全部空壳 |
| Phase 1 计划 | 只完成模板库 | ⚠️ 50% 完成 |
| Phase 2-3 | 未启动 | ❌ |

实际执行比提案好的部分：新增了 3 个提案没提但更基础的模板（叙事节奏循环控制 / 文风锚点 / 状态行为标志）。

**结论**：方向正确但执行偏离。需要补齐遗漏项和空壳 → 用户在后续会话修复，最终模板库增至 19 个（13-19），4 个参考文件全部写出实际内容。

### Pitfall

> ❌ 只看文件是否存在 → 空壳文件（只有标题）也能通过"存在性检查"
> ❌ 只看模板数量是否增加 → 漏掉了编号不一致、提案内容未实施等问题
> ✅ 用差距分析表格逐项对比提案→执行
> ✅ 区分"合理偏离"（执行更好）和"不合理遗漏"（有价值项目丢失）
> ✅ 判断完后更新提案到 v2.0 匹配实际执行，避免后续窗口困惑

## 验证代码模板

```python
import json

path = '/path/to/card.json'
with open(path, 'r', encoding='utf-8') as f:
    data = json.load(f)

entries = data['data']['character_book']['entries']
entry_dict = {e['id']: e for e in entries}

# 逐项验证对方报告中的每个结论
checks = {
    '萝莉残留': lambda: sum(
        e.get('content', '').count('萝莉') +
        sum(1 for k in e.get('keys', []) if '萝莉' in k)
        for e in entries
    ) + data['data']['description'].count('萝莉'),

    'constant条目数': lambda: sum(1 for e in entries if e.get('constant')),

    '字段缺失': lambda: sum(
        1 for e in entries
        for f in ['id','keys','secondary_keys','content','constant',
                   'enabled','selective','addMemo','use_regex','extensions']
        if f not in e
    ),

    'position分布': lambda: dict(
        (pos, sum(1 for e in entries if e.get('position') == pos))
        for pos in set(e.get('position') for e in entries)
    ),
}

for name, check in checks.items():
    result = check()
    print(f"  {name}: {result}")
```

## 实测案例

示例玄幻项目v2审查（2026-07-07）：
- 窗口A（我）：首轮报告14项，其中3项误报（uid/年龄/常驻数量）
- 窗口B（另一Hermes）：14项审查，其中3项误报（同上），2项需确认
- 交叉验证后：9项确认真实，3项误报，2项需用户确认

关键教训：**不要盲信对方的条目ID**。窗口B报"ID=12/41/47/69/113"有萝莉，实际用数组索引换算后才是正确的条目ID。
