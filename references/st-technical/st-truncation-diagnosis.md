# ST 截断诊断完整流程

## 第一步：区分截断类型

截断有两种完全不同的根因，修复方式完全不同：

| 类型 | 症状 | 根因 | 修复 |
|------|------|------|------|
| **API预设膨胀** | 第一次发消息就被截断，第二次能跑 | 系统提示总token > max_context - max_tokens | 调ST设置/精简预设 |
| **世界书过载** | 每次回复都变短或截断 | 世界书条目总token过高 | 优化关键词/减少条目 |

**关键判断方法**：如果第一次截断、第二次正常 → 大概率是API预设膨胀，不是世界书问题。

## 第二步：如果是API预设膨胀

### 诊断方法
让用户提供ST的API请求日志（ST设置 → View Logs → 找到请求），分解各部分token：

```
SYSTEM消息总token = 角色卡system_prompt + 世界书条目 + 预设规则 + H-Guide + COT + Prism + ...
ASSISTANT消息token = 开场白 + 创作者备注 + 历史回复
USER消息token = 用户输入
```

### 常见膨胀来源（实测案例）
1. **预设规则重复加载** — 活人感基准、叙事推进基准、H特写规则各出现2次 → ~8000 tokens浪费
2. **创作者长信/作者备注** — 占ASSISTANT消息 → ~3500 tokens，不在世界书里
3. **H-Guide + Prism + COT** — 每次请求全量注入 → ~3000 tokens
4. **世界书条目** — 实际只占一小部分 → ~3000 tokens

### 修复方法
1. ST设置：max_context 调到 65536+，max_tokens 调到 3000-4000
2. 检查预设为什么规则重复加载（可能是预设+角色卡双重注入）
3. 创作者备注移到角色卡描述里，或用正则脚本在非首轮删除
4. 精简不必要的预设规则

## 第三步：如果第二轮/第三轮才开始截断

**重要边界**：本节只用于 ST 运行环境排查，**不作为角色卡/世界书交付质量判定**。社区用户预设、模型安全层、破限制力度、网关输出上限各不相同；发布卡时不能把某个预设下的截断直接判为卡缺陷。

2026-07-15 示例G型卡v2 + 凝嘤嘤预设实测修正：同一测试卡后续又连续跑了 4-5 轮无截断，说明此前“第二轮截断”不能被写成稳定复现的角色卡问题。若日志中出现中段断开，应先区分：

- **卡内问题**：世界书泛 key、secondary 失效、first_mes 拉入无关深度档案、卡内 system_prompt/世界书写死过多每轮强制项。
- **运行环境问题**：用户预设强制长思考/额外模块、API response cap、模型近期安全策略变化、破限制力度不足、流式网关断流。

制卡流程只要求修第一类。第二类只能作为“用户运行环境备注/排查建议”，不能阻塞卡交付，也不能写进卡质量失败原因。

建议记录方式：

```text
本卡触发审计已通过；若个别预设/模型出现截断或回空，请优先检查该运行环境的 max response、模型安全层、预设破限制力度与历史裁剪。此类不计入角色卡结构缺陷。
```

### 负载参考（诊断信号，不是绝对红线）

> 这里的“负载”通常是脚本按字符粗略折算的诊断值，不等于 API 官方 input tokens。大型结构化卡 v4.2 实测首轮可达 7w+ 字符/10w 级请求体仍可流畅运行，说明高负载本身不等于必然截断。交付审查只看卡内问题：是否无关触发、泛 key、递归链、卡内常驻过重、卡内每轮强制项过多，以及 ST/模型实际运行是否稳定；外部用户预设导致的重复注入/破限制不足不计为卡缺陷。

| 估算负载 | 状态 | 处理原则 |
|------|------|------|
| < 4000 | ✅ 轻负载 | 通常无需为 token 修结构 |
| 4000-8000 | ✅ 正常 | 检查是否有明显误触发即可 |
| 8000-12000 | ⚠️ 偏高 | 跑触发审计，优先修泛 key/secondary/常驻 |
| > 12000 | 🔎 高负载 | 不直接判死刑；若实际卡顿/截断/回空，再按审计结果修触发质量与输出复杂度 |

### 优化4策略
1. 常驻条目 keys=[]（不带关键词）
2. 复合关键词（"{角色}身体描写" 而非 "{角色名}"）
3. 常驻转触发（只保留4-6条核心常驻）
4. 性爱规则按需加载（>800c的条目不放常驻）
