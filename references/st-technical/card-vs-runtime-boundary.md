# 角色卡质量 vs 运行环境问题边界

> 来源：2026-07-15 示例G型卡 Gv2 trigger-fix-test、凝嘤嘤/Gemini 预设截断排查后的用户纠正。

## 核心原则

发布给社区的 SillyTavern 角色卡必须尽量兼容不同预设，但不能为所有外部预设、模型、API 网关或破限制策略背锅。

**制卡流程只判定角色卡/世界书自身质量。** 运行时截断、回空、断流、叠甲等现象，需要先区分是卡内问题还是运行环境问题。不要把某个用户预设下的偶发截断写进角色卡质量失败项。

## 卡内问题：需要修卡

以下属于角色卡/世界书自身问题，必须在交付前修复：

1. 世界书硬泛 key：如 `家`、`学校`、`妈妈`、`妹妹`、`手机`、`写真` 等普通句误触发深度条目。
2. `secondary_keys` 失效：写了 secondary，但顶层 `selective=false`，导致范围绑定完全不生效。
3. first_mes 污染：开场白一次性拉入多个无关深度档案、场景、事件库。
4. 常驻过重：角色卡/世界书自身写死过多 every-turn 规则，且可改为按需触发。
5. 卡内 system_prompt 过度强制：角色卡自身要求每轮必须同时输出多种模块，导致普通预设也负担过重。
6. 人物关系错位、身份锚点错误、触发死 key、内容太薄、事件种子不可用等传统卡质量问题。

## 运行环境问题：只写备注，不判卡失败

以下属于社区用户自己的运行环境或模型/API问题，不作为角色卡质量失败原因：

1. 用户预设不同：aftertalk、math、Prism、长 thinking、长剧情档案等模块由预设注入。
2. 预设破限制力度不足：某些模型近期安全策略变化或“叠甲”导致回空/截断。
3. API 网关/端点行为：流式输出中断、response cap 与 ST 显示 max_tokens 不一致。
4. 模型临时安全策略：Gemini/兼容层/代理服务近期调整导致同卡不同时间表现不同。
5. 用户历史裁剪设置：上一轮长输出、预设模块、思考内容被完整带入下一轮。
6. 单次日志中段断，但同卡后续 4-5 轮可正常运行，无法稳定复现。

## 正确写法

当触发审计通过，但个别预设/模型出现截断时，报告应写：

```text
本卡触发审计已通过；当前日志中的截断更像运行环境问题。请检查所用预设、模型安全层、API response cap、破限制策略与历史裁剪。此类问题不计入角色卡结构缺陷。
```

不要写：

```text
本卡因为该预设下截断，所以角色卡质量不通过。
```

## 排查顺序

1. 先跑 `audit_worldbook_triggers.py`，确认卡内触发结构是否合格。
2. 若存在泛 key / secondary 失效 / first_mes 无关深度档案误触发，先修卡。
3. 若卡内触发结构合格，但某预设/模型偶发截断，只记录为运行环境排查。
4. 若同卡多轮可稳定运行，不要根据一次中段断开否定卡。
5. 发布卡时可以给用户提示“不同预设/模型表现可能不同”，但不把外部预设问题当成卡缺陷。

## 技术备注

高请求体/高字符数不是绝对红线。大型结构化卡 v4.2 首轮可达 7w+ 字符仍流畅，说明关键不是裸 token，而是触发质量、内容相关性与运行环境稳定性。
